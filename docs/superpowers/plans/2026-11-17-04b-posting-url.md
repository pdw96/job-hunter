# Job Hunter 4-1b 계획: 공고 주소로 읽기 Implementation Plan

**Goal:** 공고 넣기 화면에 주소를 넣고 `주소로 읽기`를 누르면, 앱이 그 페이지를 한 번 열어 글자를 뽑고 지금과 같은 방식으로 값을 채운다. 읽지 못하면 이유를 알리고 붙여 넣기로 넘어간다.

**배경:** 사용자는 공고를 여러 사이트에서 본다(2026-11-17 확인). 공고 글을 매번 복사해 붙여 넣는 것이 번거롭다. 공고를 앱이 찾아오는 일(자동 수집)은 설계대로 2단계에 둔다. 이번 것은 사용자가 고른 주소 하나를 대신 열어 주는 데까지다.

**미리 알 수 없는 것:** 어느 사이트가 읽히는지는 배포한 뒤 실제 주소로 넣어 봐야 안다(이 작업 환경에서는 채용 사이트에 접속할 수 없다). 그래서 "되는 곳은 되고, 안 되면 붙여 넣기"로 만든다.

**Architecture:** `postings/fetch-page.ts`가 주소를 열어 글자를 뽑는다. 페이지를 여는 부분과 HTML에서 글자를 뽑는 부분(순수 함수)을 나눠, 뒤쪽을 테스트한다. 뽑은 글은 붙여 넣은 글과 똑같이 다룬다(원문으로 보관, AI로 값 뽑기).

## Global Constraints

- 앞 계획들의 Global Constraints를 모두 따른다
- 사용자가 누를 때 그 주소 하나만 연다. 링크를 따라가거나 여러 페이지를 훑지 않는다
- 서버가 여는 주소를 제한한다: `http`/`https`만, 내부망·자기 자신을 가리키는 주소는 열지 않는다(주소가 다른 곳으로 넘길 때도 다시 검사한다)
- 한도: 전체 15초(넘겨 주기와 그림 포함), 페이지 2MB, 넘겨 주기 3번까지
- 요청에 사용자 정보를 넣지 않는다
- 로그인이 필요한 페이지를 대신 로그인해 열지 않는다

## 글자를 뽑는 방법

1. 페이지에 채용 공고 정보가 정해진 형식(JSON-LD의 `JobPosting`)으로 들어 있으면 그것을 먼저 쓴다: 회사, 직무, 마감일, 근무지, 본문
2. 그렇지 않으면 본문 글자를 쓴다: 스크립트와 스타일, 메뉴·머리말·꼬리말을 빼고 태그를 지운 글
3. 뽑은 글이 200자보다 짧으면 읽지 못한 것으로 본다(본문이 그림이거나, 나중에 불러오는 페이지다)

## 읽지 못했을 때 알리는 말

| 경우 | 알림 |
|---|---|
| 주소가 틀림, 내부 주소 | 주소를 확인해 주세요 |
| 접속이 막힘(403 등), 시간 초과 | 이 사이트는 자동으로 읽을 수 없습니다. 공고 글을 복사해 붙여 넣어 주세요 |
| 글자가 거의 없음 | 공고 글을 찾지 못했습니다. 본문이 그림이거나 로그인이 필요한 페이지일 수 있습니다. 공고 글을 복사해 붙여 넣어 주세요 |

## Tasks

### Task 1: 글자 뽑기 (순수 함수)
- `postings/page-text.ts`: `textFromHtml(html)` → 뽑은 글. JSON-LD `JobPosting`, 본문 글자, HTML 문자 표기(`&amp;` 등) 풀기
- 테스트: JSON-LD가 있는 페이지, 없는 페이지, 스크립트·메뉴 빼기, 글자가 거의 없는 페이지

### Task 2: 페이지 열기
- `postings/fetch-page.ts`: `fetchPostingText(url)`. 주소 검사, 내부 주소 막기, 한도, 넘겨 주기 따라가며 다시 검사, 글자 형식(인코딩) 맞추기
- 테스트: 주소 검사와 내부 주소 판정(순수 함수 부분), 가짜 `fetch`로 넘겨 주기·한도·오류

### Task 3: 화면
- 공고 넣기 화면 맨 위에 `공고 주소` 칸과 `주소로 읽기` 버튼
- 누르면 페이지를 열어 뽑은 글을 `공고 원문` 칸에 채우고, 이어서 값을 뽑아 "뽑은 값 확인"으로 넘어간다. 주소는 공고에 함께 저장한다
- 읽지 못하면 위 표의 말을 보여 주고, 원문 칸에 직접 붙여 넣게 한다

### Task 4: 확인
- `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build`
- 로컬 미리보기에서는 시험용 페이지를 띄워 확인한다
- 합친 뒤 사용자가 실제 공고 주소 여러 개를 넣어 보고, 읽히는 사이트와 안 읽히는 사이트를 알려 준다

## 그림으로 된 공고 읽기 (2026-11-17 사용자 요청으로 이번에 함께 만든다)

국내 공고는 본문이 그림 한 장인 경우가 흔하다. 두 가지 길로 읽는다.

- **주소로 읽을 때**: 페이지의 글이 200자보다 짧으면 본문의 큰 그림(40KB 이상, 2장까지)을 가져와 읽는다
- **직접 올릴 때**: 공고 넣기 화면에서 공고 그림이나 화면을 찍은 것을 올린다. 사이트가 막혀 있어도 쓸 수 있다

읽는 방법

- 그림은 브라우저가 읽기 좋은 크기로 줄이고(너비 1,100), 세로로 긴 그림은 위에서 아래로 조각낸다(높이 1,500, 조금 겹침, 10조각까지). 긴 그림을 통째로 보내면 작게 줄어 글자를 읽을 수 없기 때문이다
- AI가 조각들을 보고 글로 옮긴다(`postings/read-image.ts`, 사용량은 `posting_image`). 옮긴 글은 붙여 넣은 원문과 똑같이 다루고, 이어서 값을 뽑는다
- 읽을 수 없는 부분은 짐작하지 않고 `[읽을 수 없음]`으로 적게 한다
- AI 호출이 한 번 더 든다(그림 옮기기 + 값 뽑기)

## 하지 않는 것

- 페이지를 연 뒤에 내용을 불러오는 사이트를 위해 브라우저를 띄워 읽기
- 공고 목록을 훑어 여러 공고를 모으기(2단계)
- 그림 읽기의 프롬프트 점검 예시(시험용 그림 파일이 필요하다. 실제 공고 그림으로 확인한 뒤 정한다)

## 구현하면서 달라진 점

- 페이지에서 글자를 뽑는 파일은 `postings/page-text.ts`의 `contentFromHtml`이고, 본문 그림의 주소도 함께 돌려준다
- 여는 주소는 기본 포트(80, 443)만 받고, 아이디·비밀번호가 든 주소는 받지 않는다
- 로컬 미리보기는 실제로 주소를 열지 않는다(`src/dev/local-fetch-page.ts`가 정해진 결과를 돌려준다)
- AI에 그림을 보낼 수 있게 `AiMessage`에 `images`를 더했다

### 검토(Codex)에서 고친 것

- 이름을 검사한 뒤 연결할 때 다시 풀지 않고, 검사한 주소로만 연결한다(DNS 리바인딩 막기). 호스트 이름과 TLS 확인은 원래 이름으로 한다
- 시간 한도를 요청마다 따로 두지 않고 전체에 하나만 둔다(15초)
- 그림은 큰 것을 고르되 페이지에 나온 순서로 돌려준다
- 늦게 불러오는 그림의 주소(`data-src`)를 속성 순서와 상관없이 먼저 본다
- `charset="euc-kr"`처럼 따옴표가 붙은 값도 읽는다
- 그림 조각 하나가 한도를 넘으면 화질을 낮춰 다시 해 본다
- (2차) HTML을 정규식으로 지우지 않고 앞에서부터 한 번만 훑는다. 닫히지 않는 `<`가 많은 페이지에서 서버가 오래 멈추던 것을 막는다
- (2차) 압축된 응답(gzip, deflate, br)을 풀어 읽는다. 크기 한도는 푼 뒤의 크기로 잰다
- (2차) 본문을 둘 수 없는 상태 코드(205 등)에서 서버가 죽지 않게 한다
