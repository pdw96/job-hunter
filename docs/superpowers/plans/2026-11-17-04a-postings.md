# Job Hunter 4-1번 계획: 공고 넣기와 제외 조건 Implementation Plan

**Goal:** 공고 원문을 붙여 넣으면 AI가 회사명, 직무명, 마감일, 근무지, 요구 경력, 고용 형태를 뽑아 채운다. 사용자가 고쳐 저장하면, 코드가 트랙의 희망 조건과 비교해 제외 조건에 걸리는지 보여 준다. 공고 목록에서 마감이 가까운 순으로 본다.

**4번 계획을 둘로 나눈다.** 이번(4-1)은 공고를 넣고 걸러 내는 데까지다. 점수(적합도)와 지원 판단은 4-2에서 한다. 4-2의 방향은 이 문서 끝에 적는다.

**Architecture:** 새 모듈 `postings`를 만든다. AI는 원문에서 값을 뽑는 일만 하고, 제외 조건 판정은 순수 함수가 한다(AI가 "지원하지 마세요"를 정하지 않는다). 뽑은 값은 사용자가 확인하고 고친 뒤에 저장된다.

**Spec:** 설계 6.4의 앞부분(공고 넣기, 제외 조건), 6.2의 트랙 구조

## Global Constraints

- 앞 계획들의 Global Constraints, `docs/conventions.md`의 데이터 접근 규칙과 AI 사용 규칙을 모두 따른다
- 공고 원문 전체를 보존한다. 고치거나 줄이지 않는다
- AI가 뽑은 값은 화면에서 사용자가 확인한 뒤에 저장한다. 원문에 없는 값은 비워 둔다(지어내지 않는다)
- 제외 조건에 걸려도 막지 않는다. 걸린 사유를 보여 주고 사용자가 정한다
- AI 호출은 모두 `runAi()`를 거친다. 공고 원문에는 채용 담당자 연락처가 있을 수 있으므로 그대로 가린다
- PR은 구현이 끝나면 초안을 풀고, Codex 검토 결과를 확인한 뒤 사용자에게 합칠지 묻는다
- 화면은 `npm run preview:local`로 확인하고 사진을 사용자에게 보낸다

## 데이터

`postings_postings`

|---|---|
| `id`, `userId`, `trackId` | 공고는 트랙 하나에 속한다. 트랙을 지우면 함께 지워진다 |

| `deadline` | 마감일(날짜). 상시 채용이면 비움 |
| `isRolling` | 상시 채용·채용 시 마감 |
| `locationText`, `regions` | 근무지 원문 표기와, 설문의 지역 목록으로 바꾼 값(여러 개 가능) |
| `careerType` | 신입 / 경력 / 신입·경력 / 무관 |
| `minYears` | 요구 경력(년). 없으면 비움 |
| `employmentType` | 정규직 / 계약직 / 인턴 / 알 수 없음 |
| `url` | 공고 주소(선택) |
| `rawText` | 공고 원문 전체 |
| `companyNote` | 사용자가 더 붙여 넣은 글(인재상, 회사 소개). 4-2의 요구 사항 뽑기에 쓴다 |
| `status` | 관심 / 지원 / 보류 / 제외. 4-1에서는 관심으로 시작하고 보류·제외만 고를 수 있다. 지원은 4-2에서 연다 |
| `excludeOverride` | 제외 조건에 걸렸지만 진행하기로 했는가 |
| `createdAt`, `updatedAt` | |

한도: 원문 3만 자, 인재상 글 1만 자, 사용자당 공고 500건.

## 제외 조건 (순수 함수)

`postings/exclusion.ts`의 `exclusionReasons(posting, track, today)`가 걸린 사유의 목록을 돌려준다.

| 사유 | 기준 |
|---|---|
| 마감 지남 | `deadline`이 오늘보다 앞. 상시 채용은 걸리지 않는다 |
| 요구 경력이 높음 | 트랙이 경력·무관일 때: `minYears`가 내 경력(년)보다 **2년 넘게** 큼. 트랙이 신입·인턴일 때: 공고가 경력만 뽑음 |
| 근무지가 희망 밖 | 공고의 `regions`와 트랙의 희망 지역이 하나도 겹치지 않음. 트랙에 "전국 어디든"이 있거나 공고의 지역을 알 수 없으면 걸리지 않는다 |
| 고용 형태가 다름 | 공고의 `employmentType`이 트랙의 희망에 없음. 트랙이 "무관"이거나 공고가 "알 수 없음"이면 걸리지 않는다 |

값을 알 수 없으면 걸리지 않는 쪽으로 둔다(모르는 것을 이유로 제외하지 않는다).

## Tasks

### Task 1: 모듈과 테이블
- `src/modules/postings/{options,schema,input,repo}.ts`, 마이그레이션 `0011`
- `validatePosting`(입력 검사), `createPosting`, `updatePosting`, `getPosting`, `listPostings`(트랙별, 마감 가까운 순, 지난 것은 뒤로), `deletePosting`, `setStatus`
- `docs/conventions.md`의 모듈 표에 `postings`를 더한다
- 테스트: 소유자 확인, 남의 트랙에 넣을 수 없음, 정렬, 한도

### Task 2: 제외 조건
- `postings/exclusion.ts`와 테스트(위 표의 경계값 모두)

### Task 3: AI로 값 뽑기
- `postings/prompts.ts`의 `POSTING_SYSTEM`, `postings/extract.ts`의 `extractPosting(db, ai, userId, rawText, today)`
- 구조화된 답: 회사명, 직무명, 마감일(YYYY-MM-DD 또는 빈 값), 상시 여부, 근무지 원문, 지역(정해진 목록에서만), 신입/경력 구분, 요구 연차, 고용 형태
- 코드 검사: 지역과 고용 형태는 목록에 있는 값만 받는다. 마감일은 날짜 형식만 받는다. 회사명과 직무명은 원문에 글자 그대로 있는지 보고, 없으면 화면에 "원문에서 찾지 못함"으로 표시한다
- 사용량은 `purpose: "posting"`으로 기록한다
- 테스트는 가짜 AI로 한다

### Task 4: 화면
- 메뉴에 `공고`를 더한다
- `/postings`: 트랙을 고르는 탭, 공고 목록(회사, 직무, 마감까지 남은 날, 제외 사유 표시, 상태), `공고 넣기` 버튼
- `/postings/new`: 트랙 선택 → 원문 붙여 넣기(+ 주소, 인재상 글은 선택) → `읽기` → 뽑힌 값을 고칠 수 있는 폼 → `저장`. AI 없이 직접 채워 저장할 수도 있다
- `/postings/[id]`: 뽑힌 값, 제외 사유(있으면 맨 위에), 원문, `보류` / `제외` / `그래도 진행`, 고치기, 지우기
- 같은 회사·직무의 공고가 이미 있으면 저장 전에 알려 준다

### Task 5: 프롬프트 점검
- 관리의 AI 프롬프트 점검에 공고 예시 2건을 더한다: 값이 다 적힌 공고, 마감·근무지·경력이 적히지 않은 공고(비워 두는지)

### Task 6: 확인
- `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build`
- 로컬 미리보기로 넣기 → 고치기 → 저장 → 제외 사유 → 목록을 확인하고 사진을 보낸다
- 합친 뒤 사용자가 실제 공고 두세 건을 넣어 본다

## 하지 않는 것 (4-1)

- 점수와 지원 판단(4-2)
- 채용 사이트 주소에서 공고를 자동으로 읽어 오기(사이트마다 막혀 있고, 설계의 2단계 일이다)
- 회사별 지원 회차 묶기(5번 계획 이후, 지원 현황과 함께)

## 4-2의 방향 (다음 계획에서 구체화)

설계의 "배점표를 다루는 방향"을 이렇게 옮긴다.

- **요구 사항 뽑기**: AI가 공고와 인재상 글에서 요구 사항을 필수 / 우대로 나눠 목록으로 뽑는다. 각 요구 사항에는 원문의 구절이 붙는다
- **경험과 맞대기**: 요구 사항마다 확인됨·부분 확인 경험 중 근거가 되는 것을 AI가 짚는다. 근거 없는 요구 사항은 "부족한 점"으로 남는다. 기록에 없는 것은 쓰지 않는다
- **점수 둘**
  - 원하는 정도 = 근무지, 분야 (내가 바라는 조건에 얼마나 맞는가)
  - 자격이 맞는 정도 = 직무 일치(필수 요구 사항을 덮은 비율), 경력 요건, 우대 요건(우대를 덮은 비율)
  - 각각 100점 만점이고, 설문의 중요도 순서가 그 안의 배점이 된다
- 점수는 순서를 정하는 표다. 붙을 확률이라고 쓰지 않는다
- 지원을 고르면 그때의 점수와 배점을 그대로 저장한다
