# Job Hunter 4-2번 계획: 점수와 지원 판단 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 공고 화면에서 `점수 보기`를 누르면 AI가 공고의 요구 사항을 필수·우대로 뽑고, 요구 사항마다 근거가 되는 내 경험을 짚는다. 코드가 그 결과와 트랙의 희망 조건으로 "원하는 정도"와 "자격이 맞는 정도"를 100점 만점으로 매긴다. 사용자는 점수와 부족한 점을 보고 지원 / 보류 / 제외를 고르고, 지원을 고르면 그때의 점수와 배점이 저장된다.

**Architecture:** AI는 요구 사항 뽑기와 경험 맞대기만 한다. 점수는 순수 함수(`postings/score.ts`)가 화면을 그릴 때마다 계산한다. 그래서 경험을 지우거나 확인을 풀면 점수에서 바로 빠진다. AI 결과는 공고 행의 `analysis` 칸에, 지원할 때의 점수는 `appliedScore` 칸에 둔다(새 테이블 없음). 경험 후보는 `experiences` 모듈의 함수로 받는다.

**Tech Stack:** Next.js 16(App Router), Drizzle + Postgres(테스트는 PGlite), zod, Vitest

**Spec:** `docs/superpowers/specs/2026-11-16-job-hunter-design.md`의 6.4 "점수", "배점표를 다루는 방향", "지원 판단". 방향은 `docs/superpowers/plans/2026-11-17-04a-postings.md`의 "4-2의 방향"

## 정한 것

- 「결정」(2026-11-17, 사용자) 원하는 정도 = **근무지, 분야**. 고용 형태는 설계에 적혀 있지만 설문의 중요도 순서에 없고 이미 제외 조건으로 걸러지므로 넣지 않는다. 설문은 바꾸지 않는다
- 자격이 맞는 정도 = 직무 일치, 경력 요건, 우대 요건
- 각 점수의 배점은 트랙에 저장된 `weights`(중요도 1~5위가 30/25/20/15/10)를 묶음 안에서 그대로 비율로 쓴다. 예: 근무지 25, 분야 15이면 원하는 정도에서 근무지가 25/40
- 알 수 없는 항목(공고에 근무지가 없음, 필수 요구 사항이 없음 등)은 그 묶음에서 빼고 남은 배점으로 나눈다. 묶음 전체를 모르면 점수를 "알 수 없음"으로 둔다
- 근거로 쓰는 경험: 확인됨·부분 확인이고, 그 트랙에서 "제외"가 아닌 것(설계 6.3: "요약만"도 채점 근거로 쓴다). 수치는 AI에게 보내지 않는다(설계 6.4: 수치는 점수 근거로 인용하지 않는다)
- 점수는 `점수 보기`를 누를 때만 AI를 부른다(AI 호출 1번, 저장하면 자동으로 부르지 않는다)
- 지원은 점수를 본 뒤에만 고를 수 있다(설계: 지원서를 쓰기 전에 채점한다). 제외 사유가 있어도 막지 않는다
- 화면 문구: "점수는 붙을 확률이 아니라, 어느 공고에 먼저 시간을 쓸지 정하는 순서입니다"

## Global Constraints

- 앞 계획들의 Global Constraints, `docs/conventions.md`의 데이터 접근 규칙과 AI 사용 규칙을 모두 따른다
- AI 호출은 `runAi()`를 거치고 `purpose: "posting_match"`로 기록한다. 모델은 `claude-sonnet-5-5`(바꾸지 않는다)
- AI에게 보내지 않는 것: 연락처, 이메일, 사용자 id, 경험의 수치와 증빙 메모, 미확인 경험, 그 트랙에서 제외한 경험
- 기록에 없는 것을 근거로 쓰지 않는다: 없는 경험을 가리키거나 원문에 없는 구절을 인용한 결과는 점수에 넣지 않는다
- 배점을 자동으로 고치지 않는다. 지원할 때 저장한 점수는 나중에 설문·경험이 바뀌어도 바뀌지 않는다
- 점수를 "합격 가능성", "확률"로 쓰지 않는다
- 화면은 로컬 미리보기로 확인하고 사진을 사용자에게 보낸다

## Review Focus

1. 근거였던 경험을 지우거나, 확인을 풀거나, 트랙에서 제외함 → 그 근거는 점수와 화면에서 바로 빠진다 (Task 2 `usable` 테스트, Task 4 화면이 지금의 후보로 계산)
2. 점수를 본 뒤 공고 원문이나 인재상 글을 고침 → 예전 요구 사항이 남지 않고 다시 보게 한다 (Task 1 테스트)
3. 확인된 경험이 하나도 없음 → 오류가 아니라 요구 사항이 모두 "부족한 점"이고 자격 점수 0 (Task 2, Task 3 테스트)
4. AI가 원문에 없는 요구 사항이나 없는 경험을 지어냄 → 점수에 들어가지 않고 "원문에서 찾지 못함"으로 보인다 (Task 3 테스트)
5. 지원한 뒤 설문(배점)이나 경험이 바뀜 → 저장한 점수는 그대로 (Task 1 테스트)

## Task 2: 점수 계산 (순수 함수)

**Files:**
- Create: `src/modules/postings/score.ts`, `src/modules/postings/score.test.ts`
- Modify: `src/modules/postings/options.ts`(아래 상수)

**Interfaces:**
- Consumes: Task 1의 타입, `tracks/options.ts`의 `Criterion`, `tracks/survey.ts`의 `experienceMode`
- Produces:
  ```ts
  export const DESIRE_CRITERIA = ["location", "field"] as const satisfies readonly Criterion[];
  export const FIT_CRITERIA = ["jobMatch", "experience", "preferred"] as const satisfies readonly Criterion[];
  export type ScoreInput = {
    posting: { regions: string[]; careerType: CareerType; minYears: number | null };
    track: { regions: string[]; applicantType: ApplicantType; experienceMonths: number | null; weights: Record<Criterion, number> };
    analysis: PostingAnalysis | null;
    usable: ReadonlySet<string>; // 지금 근거로 쓸 수 있는 경험 id (listEvidenceCandidates의 id)
  };
  export function scorePosting(input: ScoreInput): PostingScore;
  export function requirementLevel(requirement: Requirement, usable: ReadonlySet<string>): "full" | "partial" | "none";
  ```
- 상수(`options.ts`): `LOCATION_BY_RANK = [1, 0.85, 0.7, 0.55, 0.4]`, `FIELD_SCORES = { same_job: 1, same_field: 0.5, other: 0 }`, `MATCH_SCORES = { full: 1, partial: 0.5, none: 0 }`

**항목별 점수 (0~1, 모르면 null)**

| 항목 | 규칙 |
|---|---|
| 근무지 | 공고 `regions`가 비면 null. 트랙에 `anywhere`면 1. 아니면 트랙 희망 지역 중 겹치는 것의 가장 앞 순위 i → `LOCATION_BY_RANK[i]`, 겹치지 않으면 0 |
| 분야 | `analysis`가 없으면 null. `FIELD_SCORES[analysis.field.level]` |
| 경력 요건 | `experienceMode`가 `entryLevelOk`(신입·인턴): 공고가 `experienced`면 0, 아니면 1. `compareYears`(경력·무관): 공고가 `new`면 0.5. `minYears`가 null이면 1. 아니면 `gap = minYears*12 - (experienceMonths ?? 0)`; gap ≤ 0 → 1, ≤ 12 → 0.7, ≤ 24 → 0.4, 그 위 → 0 |
| 직무 일치 | `analysis`가 없거나, `quoteFound`인 필수 요구 사항이 없으면 null. 그것들의 `MATCH_SCORES[requirementLevel]` 평균 |
| 우대 요건 | 같은 방식으로 우대 요구 사항 |

- `requirementLevel`: `evidence` 중 `experienceId`가 `usable`에 있는 것의 가장 높은 `level`, 없으면 `"none"`
- 묶음 점수 = `round(Σ(weight × score) / Σ(weight, score가 null 아님) × 100)`. 묶음의 항목이 모두 null이면 null
- `criteria`에는 다섯 항목 모두 `{ score, weight: track.weights[c] }`를 담는다

- [ ] **Step 1: 실패하는 테스트를 쓴다** (배점은 jobMatch 30, location 25, experience 20, field 15, preferred 10)
  - "근무지 1순위·같은 분야 다른 직무면 원하는 정도 81": regions `["seoul","gyeonggi"]`, 공고 `["seoul"]`, field `same_field` → `(25×1 + 15×0.5)/40×100 = 81.25` → `81`
  - "근무지가 2순위면 0.85, 겹치지 않으면 0, 전국이면 1, 공고 근무지가 없으면 null이고 분야만으로 매긴다"(field `same_job`이면 desire 100)
  - "경력 요건 경계": 경력 트랙 36개월, minYears 3 → 1 / 4 → 0.7 / 5 → 0.4 / 6 → 0; 신입 트랙에 `experienced` → 0, `both` → 1; 경력 트랙에 `new` → 0.5
  - "직무 일치는 필수 요구 사항을 덮은 비율": 필수 2개(full, none) + 원문에서 찾지 못한 필수 1개(full) → 0.5
  - "근거 경험이 usable에 없으면 none으로 본다"(Review Focus 1)
  - "확인된 경험이 없으면 직무 일치·우대가 0으로 들어간다": usable 빈 집합, 필수 1·우대 1, 경력 1 → fit = `(30×0 + 20×1 + 10×0)/60×100 = 33`(Review Focus 3)
  - "analysis가 없으면 분야·직무 일치·우대가 null이고 fit은 경력 요건만으로 매긴다"
  - "필수도 우대도 없으면 jobMatch·preferred null"

- Produces:
  ```ts
  export type AnalyzeInput = { rawText: string; companyNote: string | null; jobNames: string[]; majorName: string; candidates: EvidenceCandidate[] };
  // 저장하지 않는다. 프롬프트 점검(Task 5)도 이것을 쓴다
  export async function analyzeText(db: Db, ai: AiClient, userId: string, input: AnalyzeInput, now?: Date):
    Promise<{ ok: true; value: PostingAnalysis } | { ok: false; reason: "over_limit" | AiFailure }>;
  export async function analyzePosting(db: Db, ai: AiClient, userId: string, postingId: string, now?: Date):
    Promise<{ ok: true; value: PostingAnalysis } | { ok: false; reason: "not_found" | "changed" | "over_limit" | AiFailure }>;
  ```

**AI에게 보내는 글** (user 메시지 하나, 칸마다 `[이름]` 머리)
- `[지원 직무]` jobNames를 `, `로, `[분야]` majorName, `[공고 원문]`, `[인재상·회사 소개]`(없으면 "없음")
- `[경험 기록]` 후보마다 `E1`, `E2` …(순서대로 붙인 별명. 실제 id는 보내지 않는다): 이름, 구분, 소속·기관, 직무·역할, 기간, 상황, 본인이 한 일, 결과, 하지 않은 것. 후보가 없으면 "없음"
- `effort: "medium"`, `maxTokens: 8000`

**답의 모양 (zod)**
```ts
{ field: { level: "same_job" | "same_field" | "other", reason: string },
  requirements: { kind: "required" | "preferred", text: string, quote: string,
                  evidence: { exp: string, level: "full" | "partial", why: string }[] }[] }
```

**`ANALYZE_SYSTEM`에 담을 것** (문구는 구현자가 쓴다)
- 공고와 인재상 글에서 지원자에게 요구하는 것을 하나씩 뽑는다. "자격 요건·필수"는 required, "우대"는 preferred. 구분이 없으면 required. 담당 업무 설명은 그 일을 해 본 경험을 요구하는 것으로 보고 required로 뽑는다. 복리후생·회사 소개는 뽑지 않는다
- `quote`는 원문 구절을 글자 그대로, `text`는 짧게 다듬은 요구 사항
- `evidence`는 그 요구 사항을 실제로 뒷받침하는 경험의 별명만. 비슷한 낱말이 있다고 짚지 않는다. "하지 않은 것"에 걸리면 짚지 않는다. 일부만 덮으면 partial. 근거가 없으면 빈 배열(그것이 "부족한 점"이 된다)
- `why`는 공고의 어느 말과 경험의 어느 내용이 겹치는지 한 문장. 기록에 없는 내용과 숫자를 쓰지 않는다
- `field`: 공고의 직무가 지원 직무 중 하나와 같으면 same_job, 같은 분야의 다른 직무면 same_field, 아니면 other
- 점수와 합격 가능성은 말하지 않는다

**코드 검사** (`analyzeText` 안)
- 요구 사항은 앞에서 30개까지. `text`는 다듬어 200자까지, 빈 것은 버린다. `quote`는 300자까지
- `quoteFound` = 공백·대소문자를 무시하고 `quote`가 원문+인재상 글에 들어 있는가(빈 `quote`는 false)
- `evidence`: 별명이 후보에 없으면 버린다. 같은 경험은 처음 것만. 별명을 실제 id로 바꾼다
