# Job Hunter 5-2번 계획: 이력서 공통본·맞춤본 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 트랙마다 이력서 공통본을 둔다. 확인된 경험 중 그 트랙에서 "사용"·"요약만"인 것으로 AI가 경험마다 이력서 줄을 쓰고, 사용자가 줄을 고치고 순서를 바꾸고 뺀다. 지원 공고마다 맞춤본을 둔다. AI가 공고에 맞춰 강조할 경험과 순서를 근거와 함께 제안하고, 사용자가 승인하면(요약만 경험도 직접 올릴 수 있다) 공통본을 복사해 강조한 경험만 공고에 맞춰 다시 쓴다. 코드가 금지 표현·기록에 없는 숫자·바뀐 경험을 표시한다.

**Architecture:** 새 테이블 `applications_resumes` 하나(「결정」 2026-11-18, 사용자). 공통본은 `posting_id`가 비고 트랙마다 1행, 맞춤본은 지원 공고마다 1행. 이력서 내용은 경험별 항목(`ResumeEntry`) 배열을 jsonb로 두고, 항목마다 머리(이름·소속·역할·기간, 코드가 기록에서 만든다)와 줄(AI가 쓰거나 사용자가 고친다)을 갖는다. 행의 `version`이 저장마다 오르고, 화면이 읽은 `version`과 같을 때만 저장한다. 검사는 5-1처럼 화면을 그릴 때마다 지금의 경험으로 계산하는 순수 함수(`resume-check.ts`)다.

**Tech Stack:** Next.js 16(App Router), Drizzle + Postgres(테스트는 PGlite), zod, Vitest

**Spec:** `docs/superpowers/specs/2026-11-16-job-hunter-design.md`의 6.3(사용 범위: 요약만은 이력서에 한두 줄, 맞춤본에서 직접 올릴 수 있음; 하지 않은 것과 금지 표현; 수치), 6.5 "이력서", 6.6(연락처는 파일을 만들 때만 넣는다 → 이력서 내용에 넣지 않는다), 2의 반목표. 5-1 계획 `docs/superpowers/plans/2026-11-18-05a-cover-letter.md`의 모듈과 함수를 다시 쓴다

## 정한 것

- 「결정」(2026-11-18, 사용자) 새 테이블은 `applications_resumes` 하나. 공통본과 맞춤본이 같은 편집 코드를 쓴다
- 공통본 후보 = 확인됨이고 그 트랙에서 "사용" 또는 "요약만"인 경험. "사용"은 자세히(2~4줄), "요약만"은 요약(1~2줄). 줄 수는 코드가 자른다(자세히 4줄, 요약 2줄, 한 줄 150자)
- 항목의 머리(이름, 소속·기관, 직무·역할, 기간)는 AI가 아니라 코드가 기록에서 만든다. 줄만 AI가 쓴다. 학력·자격처럼 줄이 없는 항목도 된다
- 섹션은 구분(kind)으로 묶고 순서는 경력 → 프로젝트 → 교육 → 학력 → 자격 → 기타 → 공백기. 섹션 안의 순서는 배열 순서이고 처음에는 시작 월이 늦은 것부터(`listWritingSources`와 같은 순서). 새로 넣는 항목은 그 섹션 끝에 붙는다
- 공통본 다듬기(AI 없음): 항목의 줄 고치기(한 줄씩, 8줄·150자까지), 섹션 안에서 위로·아래로, 빼기. 뺀 항목은 "넣을 수 있는 경험"에 다시 보인다. AI로는 항목 다시 쓰기(고른 항목만, 고친 줄이 있으면 덮어쓴다는 확인)와 새 경험 넣기
- 직접 고친 줄은 `edited: true`이고 숫자 검사를 하지 않는다(5-1과 같다). 금지 표현은 계속 본다. 줄을 고칠 때 글이 그대로인 줄은 `edited`를 그대로 둔다
- 맞춤본은 지원 판단이 "지원"인 공고에서만 만들고 고친다(지원이 아니게 되면 읽기만). 공통본이 없으면 만들 수 없고 공통본 화면으로 보낸다
- 맞춤본 고르기: AI는 공통본에 있고 지금 "사용"인 경험만 후보로 받아 강조할 것을 1~5개, 강조 순서대로, 이유 한 문장과 함께 고른다. 수치는 보내지 않는다. "요약만" 경험은 AI 후보가 아니고, 사용자가 직접 체크해 올릴 수 있다(설계 6.3). 아무것도 체크하지 않고 만들면 AI 없이 공통본을 그대로 복사한다
- 맞춤본 만들기: 공통본 내용을 복사하고, 체크한 경험(5개까지)은 자세히·강조로 바꿔 그 섹션 맨 위로 체크 순서대로 옮긴 뒤 AI가 공고에 맞춰 그 항목의 줄만 다시 쓴다. 나머지 항목은 공통본 그대로. 다시 만들면 맞춤본을 덮어쓴다(확인 한 번). 만든 뒤 공통본을 고치면 "공통본을 고친 뒤입니다"만 보인다(자동으로 따라가지 않는다)
- 맞춤본도 다듬기(줄 고치기, 위아래, 빼기, 다시 쓰기, 새 경험 넣기)가 공통본과 같다. 맞춤본에서 강조한 항목을 다시 쓰면 공고를 함께 보낸다
- 검사(저장·복사를 막지 않고 표시만): 쓸 수 없게 된 경험(지움, 확인 풀림, 트랙에서 제외), 바뀐 경험(버전), 범위가 바뀜(공통본에서 사용↔요약만이 바뀌어 분량이 다름), 금지 표현, 기록에 없는 숫자, 넣을 수 있는데 없는 경험, (맞춤본) 공통본을 고친 뒤
- 이력서 전체를 글로 `복사`할 수 있다(내려받기는 6번 계획)
- AI 용도는 `resume_write`, `resume_emphasis`. 관리 화면의 프롬프트 점검 호출은 16번 → 18번
- 공통본에 넣는 항목은 40개까지(`RESUME_LIMITS.entries`). 넘으면 앞의 40개만 쓴다

## Global Constraints

- 앞 계획들의 Global Constraints, `docs/conventions.md`의 데이터 접근 규칙과 AI 사용 규칙을 모두 따른다
- AI 호출은 `runAi()`를 거친다. 모델은 `claude-sonnet-5-5`(바꾸지 않는다)
- AI에게 보내지 않는 것: 연락처, 이메일, 사용자 id, 경험의 실제 id(별명 E1, E2 …만), 증빙 메모, 확인됨이 아니거나 그 트랙에서 "제외"인 경험, 루브릭 수치가 충족이 아닌 경험의 수치. 강조 고르기에는 수치를 보내지 않는다
- 기록에 없는 경험·수치·역할을 쓰지 않는다. AI가 돌려준 내용은 코드가 검사한 뒤에만 저장하고, 시간이 걸리는 AI 작업은 읽었을 때의 `version` 그대로일 때만 저장한다
- 반목표(지어낸 수치, 금지 표현, 어떤 경험에서 나왔는지 모르는 줄, 다른 사용자의 기록)는 자동 테스트로 확인한다. 이력서의 줄은 항목에 속하므로 늘 근거 경험이 하나다
- 화면은 로컬 미리보기로 확인하고 사진을 사용자에게 보낸다

## Review Focus

1. 공통본을 만든 뒤 경험을 고치거나, 확인을 풀거나, 트랙에서 요약만·제외로 바꾸거나, 지움 → 그 항목에 "바뀜"/"범위가 바뀜"/"쓸 수 없음"이 보이고, 다시 쓰기는 쓸 수 없는 경험을 AI에 보내지 않는다 (Task 2 `checkResume` 테스트, Task 3 테스트)
2. 확인된 사용·요약만 경험이 하나도 없는 트랙 → AI를 부르지 않고 "이 트랙에 쓸 수 있는 확인된 기록이 없습니다"와 AI 인터뷰 버튼 (Task 3 테스트, Task 6 화면)
3. AI가 쓰는 사이 다른 탭에서 줄을 고치거나 항목을 옮김 → 저장하지 않고 `changed`, 고친 줄이 덮어써지지 않는다 (Task 3, Task 5 테스트)
4. 맞춤본에서 요약만 경험을 직접 올림, 쓸 수 없는 경험 id를 보냄, 6개를 보냄 → 요약만은 자세히로 쓰이고, 쓸 수 없는 id는 버리며, 6개는 `too_many_selected`이고 AI를 부르지 않는다 (Task 5 테스트)
5. 남의 트랙·남의 공고·남의 이력서 id, 지원에서 보류로 바꾼 공고 → `not_found` / `not_apply`, 남은 맞춤본은 읽힌다 (Task 1, Task 4, Task 5 테스트)
