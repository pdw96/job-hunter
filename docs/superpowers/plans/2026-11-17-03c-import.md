# Job Hunter 3-3번 계획: 가져오기 (붙여 넣기 · PDF · 워드 · 주장별 확인) Implementation Plan

**Goal:** 기존 이력서나 자기소개서를 붙여 넣거나 파일로 올리면, AI가 경험 단위로 쪼개 기록 초안을 만든다. 초안의 핵심 주장(역할 표현, 수치, 기간)을 하나씩 버튼으로 확인하고, 모두 확인해야 그 기록을 "확인됨"으로 만들 수 있다.

**배경:** 사용자의 기존 경력 자료는 AI로 작성된 것이다(2026-11-17 확인). 실제보다 부풀려진 표현이나 근거 없는 수치가 섞여 있을 수 있다. 그래서 가져온 내용을 사실이 아니라 **확인이 필요한 주장**으로 다룬다. 기록 전체를 한 번에 "내용이 맞습니다"로 확인하는 방식만으로는 부족하다.

**Architecture:** `experiences` 모듈에 가져오기와 주장을 더한다. 무엇이 주장인지는 AI에만 맡기지 않는다. **숫자와 기간과 과장되기 쉬운 낱말은 코드가 찾고**, AI는 거기에 더해 문맥상 과장으로 읽힐 표현을 짚는다. 주장을 어떻게 닫는지와 언제 확인을 허용하는지는 순수 함수로 두고 테스트한다. 파일에서 글자를 뽑는 일은 `import-text` 한 곳에 모은다.

**Spec:** 설계 6.3의 "쌓는 방법"과 "가져온 자료는 주장으로 다룬다", 8장의 4단계

## Global Constraints

- 앞 계획들의 Global Constraints, `docs/conventions.md`의 데이터 접근 규칙과 AI 사용 규칙을 모두 따른다
- 원본 파일은 저장하지 않는다. 글자를 뽑은 뒤 버린다. 뽑은 글 전체도 저장하지 않는다(주장의 인용 구절만 남는다)
- AI에게 보내기 전에 `redactContacts`로 연락처를 가린다. 화면에 `연락처는 지우고 올리는 것이 안전합니다`라고 알린다
- 가져온 기록은 원본에 뭐라고 적혀 있든 모두 미확인으로 저장한다
- AI 호출은 모두 `runAi()`를 거친다
- PR은 구현이 끝나면 초안을 풀고, **Codex 검토 결과를 확인한 뒤** 사용자에게 합칠지 묻는다
- 화면은 `npm run preview:local`로 확인하고 사진을 사용자에게 보낸다

## 주장 규칙

**주장의 종류**

| 종류 | 무엇 | 누가 찾나 |
|---|---|---|
| `period` 기간 | 기록의 시작 월과 끝 월 | 코드 (기간이 있으면 항상 1개) |
| `metric` 수치 | 수치 칸의 각 줄, 그리고 상황·한 일·결과에 있는 숫자가 든 구절 | 코드 |
| `role` 역할 표현 | 주도, 총괄, 리드, 단독, 전담, 책임, 이끌 같은 낱말이 든 구절 | 코드 |
| `role` 역할 표현 | 문맥상 실제보다 크게 들릴 수 있는 구절 | AI |

같은 구절이 겹치면 하나로 합친다. 기록 하나에 30개까지.

**버튼과 결과**

| 종류 | 버튼 | 결과 |
|---|---|---|
| 모두 | 맞음 | `confirmed`. 닫힘 |
| 수치 | 숫자 모름 | 수치 칸의 줄이면 그 줄을 지우고 `removed`로 닫힘. 본문 속 숫자면 `needs_fix` |
| 역할 표현 | 과장임 | 그 구절을 금지 표현에 넣고(사용자가 직접 고른 것이므로 바로 들어간다) `needs_fix` |
| 모두 | 틀림 / 고칠게요 | `needs_fix` |

**`needs_fix`는 어떻게 닫히나**: 기록을 고쳐 저장했을 때 그 구절이 본문에 더 이상 없으면 자동으로 `fixed`가 된다. 기간 주장은 기간이 바뀌면 `fixed`가 된다. 고치는 방법은 둘이다: 입력 화면에서 직접 고치기, 또는 `지금 보완하기` 인터뷰(과장이라고 표시한 구절과 틀렸다고 한 것을 AI에게 알려 주고 실제 범위를 묻게 한다).

**확인의 조건**: `pending`이나 `needs_fix`인 주장이 하나라도 있으면 `내용이 맞습니다`를 누를 수 없다(`confirmExperience`가 `claims_pending`으로 거부한다). 주장이 모두 닫힌 뒤의 흐름은 다른 기록과 같다(AI 판정, 본인 확인).

**내용을 고치면**: 본문에 새로 생긴 숫자나 과장 낱말은 새 `pending` 주장이 된다. 이미 `confirmed`인 주장은 그 구절이 그대로 남아 있는 한 유지한다. 직접 입력했거나 인터뷰로 만든 기록(가져온 것이 아닌 기록)에는 주장을 만들지 않는다.

## 빌더가 정한 것 (사용자가 바꿀 수 있음)

| 항목 | 정한 내용 |
|---|---|
| 파일 | PDF, 워드(.docx), 글 파일(.md, .txt, .csv). 한 번에 하나, 4MB까지. 한글(.hwp)과 옛 워드(.doc)는 지원하지 않는다 |
| 노션 | 사용자의 자료는 노션에 있다(2026-11-17 확인). 노션 연동(API)은 만들지 않는다. 페이지를 복사해 붙여 넣거나, 노션의 `내보내기 → Markdown & CSV`로 받은 .md / .csv 파일을 올린다. 화면에 이 방법을 안내한다 |
| 글자 없는 PDF | 스캔한 PDF는 글자를 읽을 수 없다고 알리고 끝낸다(글자 인식은 하지 않는다) |
| 길이 | 뽑은 글이 4만 자를 넘으면 나눠서 올리라고 알린다(자르지 않는다) |
| 한 번에 만드는 기록 | 12건까지. 더 있으면 AI가 알려 주고, 나머지는 나눠서 올린다 |
| 미리 고르기 | 없다. AI가 쪼갠 초안을 모두 미확인 기록으로 저장하고, 결과 화면에서 필요 없는 것을 지운다 |
| 같은 자료를 두 번 올리면 | 막지 않는다. 결과 화면과 목록에서 지운다 |
| 가져온 기록 표시 | 목록에 `가져옴`과 `확인할 주장 N개` |
| 트랙별 사용 범위 | 다른 기록과 같이 모든 트랙에서 "사용"으로 시작 |

- [ ] **Step 1: 실패하는 테스트**
  - 규칙: "장애 80% 감소"와 "5건에서 1건"이 수치 주장으로, "프로젝트를 주도했다"가 역할 주장으로, 기간이 기간 주장으로 잡힌다. 숫자가 없는 문장과 과장 낱말이 없는 문장은 잡히지 않는다. 연도만 있는 기간 표기는 수치 주장이 아니다

  - 직접 입력한 기록에는 주장이 생기지 않는다
  - 다른 사용자의 주장은 읽히지 않고 답할 수 없다. 기록을 지우면 주장도 지워진다

### Task 3: AI로 쪼개기

**Files:** Create `src/modules/experiences/import.ts`, `import.test.ts`. Modify `prompts.ts`, `src/modules/ai/client.ts`(`purpose`에 `import` 추가)

**Interfaces:**

  4. `findClaims` + AI의 `roleClaims`를 합쳐 주장을 만든다. AI가 준 구절이 초안 본문에 실제로 없으면 버린다
  5. 기록(`source: "import"`, 미확인)과 주장을 한 트랜잭션으로 저장한다

- [ ] **Step 2: 초안을 풀고 Codex 검토를 기다린다.** 지적을 확인해 맞는 것을 고친다
- [ ] **Step 3: 사용자 확인 후 합친다.** 배포 기록에서 마이그레이션 적용을 확인한다
- [ ] **Step 4: 사용자가 실제 주소에서 프롬프트 점검을 돌리고, 자기 자료를 가져와 본다.** 결과를 보고 프롬프트와 주장 규칙을 고친다
- [ ] **Step 5: 4번 계획(공고와 적합도)을 작성한다.** 설계의 "배점표를 다루는 방향"을 구체화한다

## 이 계획에서 하지 않는 것

- 한글(.hwp) 파일, 스캔한 PDF의 글자 인식, 이미지
- 가져오기 전에 초안을 골라 담는 화면
- 주장을 AI가 대신 고쳐 써 주는 기능: 고치는 것은 사용자가 직접 하거나 보완 인터뷰로 한다. AI가 "실제로는 이 정도였을 것"이라고 추측해 낮춰 쓰는 것도 지어내기다

## 구현하면서 달라진 점

- 과장 낱말로 찾은 역할 주장에서 `과장임`을 누르면, 문장 전체가 아니라 그 낱말(예: `주도`)이 금지 표현에 들어간다. AI가 짚은 구절은 그 구절이 들어간다
- 숫자 검사가 `2023.03` 같은 날짜 표기를 소수로 읽던 것을 고쳤다(연도와 월로 본다). 인터뷰 초안의 숫자 경고에도 적용된다
- 숫자 검사는 숫자만 비교한다. 원본의 다른 곳에 같은 숫자가 있으면(예: 3월의 3과 "3배") 지어낸 숫자를 놓친다. 그래도 그 구절은 수치 주장으로 잡혀 사용자가 확인하게 된다
- 서버에서 기록이 바뀌면(주장에 답해 금지 표현이 추가되거나 수치 줄이 지워질 때) 입력 폼이 그 값을 따라가게 했다. 전에는 "저장하지 않은 변경"으로 착각해 버튼이 막혔다. AI가 제안한 금지 표현을 승인할 때도 같은 문제가 있었다
- 가져오기의 준비 단계(`requestImport`)를 저장과 분리했다. 프롬프트 점검이 저장 없이 같은 과정을 돌린다

### 검토(Codex)에서 고친 것

- 긴 문장(200자 초과)은 잘라 버리지 않고 조각으로 나눠, 뒤쪽의 숫자와 과장 낱말도 주장으로 잡는다.
- 수치 칸과 본문에 같은 구절이 있을 때 "숫자 모름"을 누르면, 수치 줄은 지우되 본문에 남아 있는 동안은 주장을 닫지 않는다.
- 산출 근거에 원본에 없던 숫자가 있으면 가져올 때 그 근거를 버린다.
- 고쳐서 닫힌 옛 주장은 30개 한도를 차지하지 않는다. 자리가 모자라면 오래된 것부터 지운다.
- (2차) 긴 수치 줄도 조각으로 나눠 뒤쪽 숫자를 묻는다. 그 숫자를 고치면 주장이 닫힌다.
- (2차) 주장으로 훑지 않는 칸(이름, 소속, 역할, 하지 않은 일, 증빙 메모)에 원본에 없던 숫자가 있으면 그 구절도 "고쳐야 함" 주장으로 만든다.
- (2차) 숫자 대조에서 날짜로 보는 것은 연도(19xx, 20xx)와 월(1~12)일 때뿐이다. "1200.50만원" 같은 소수는 그대로 둔다.
- (2차) "숫자 모름"으로 수치 줄을 지우면 기록을 고쳤을 때와 같이 예전 판정과 후보를 지운다. 루브릭 저장 도우미를 `rubric-store.ts`로 옮겼다.
- (3차) 주장을 찾을 때도 소수 금액을 날짜로 보지 않는다.
- (3차) "숫자 모름"으로 수치 줄을 지우면 그 줄에서 나온 다른 주장도 함께 정리한다.
- (3차) 기록을 고친 뒤 열린 주장이 있으면, 판정 대상이 아닌 칸(이름, 증빙 메모)을 고쳤더라도 본인 확인을 푼다.
- (4차) 전각 숫자(７３)가 든 문장도 수치 주장으로 잡는다.
- (5차) "12년간", "3년 동안" 같은 기간 숫자는 날짜로 보지 않고 수치 주장으로 잡는다.
- (5차) 금지 표현이 30개로 가득 차 있으면 "과장임"을 받지 않고, 하나를 지우라고 알린다.
