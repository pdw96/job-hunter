# Job Hunter 1번 계획: 기반 (로그인 · 허용 이메일 · 사용자 격리) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 허용된 이메일의 구글 계정만 로그인할 수 있고, 관리자가 허용 목록을 관리하며, 모든 사용자 데이터가 소유자에게만 보이는 빈 앱을 Vercel에 올린다.

**Architecture:** Next.js App Router 한 프로젝트에 화면과 서버를 함께 둔다. ERP처럼 데이터를 모듈 단위로 관리한다: 모듈마다 폴더 `src/modules/<모듈>/`가 있고, 그 모듈의 테이블 정의(`schema.ts`)와 데이터 접근 함수(`repo.ts` 등)를 함께 둔다. 테이블 이름은 `<모듈>_<이름>`이다. 다른 모듈의 테이블은 직접 조회하지 않고 그 모듈의 함수를 통해서만 쓴다(1번 계획의 모듈: `auth` 로그인, `access` 허용 이메일, `profile` 연락처). 데이터 접근은 `src/modules/<모듈>/repo.ts`의 함수로만 하고, 모든 함수의 첫 인자는 `userId`다. `userId`는 서버에서 `requireUser()`로만 얻는다. 테스트는 메모리 Postgres(PGlite)에 실제 마이그레이션을 적용해 돌린다.

**Tech Stack:** Next.js(최신, App Router, TypeScript, Tailwind) · Better Auth(구글 로그인, Drizzle 어댑터) · Drizzle ORM + drizzle-kit · Neon Postgres(`drizzle-orm/neon-serverless`) · PGlite(테스트) · Vitest · npm · Node 24

**Spec:** `docs/superpowers/specs/2026-11-16-job-hunter-design.md` (이 계획은 6.1, 6.6의 연락처 분리, 7장, 8장의 1단계를 구현한다)

## Global Constraints

- 화면 언어는 한국어
- 로그인은 구글 로그인만. 이메일·비밀번호 로그인은 켜지 않는다
- 허용 목록에 없는 계정은 사용자 행이 만들어지지 않는다. 안내 문구는 정확히 `초대받은 사람만 쓸 수 있습니다`
- 최초 관리자는 환경 변수 `ADMIN_EMAIL`의 이메일 한 개다
- 모든 사용자 데이터 조회·수정은 로그인한 사용자의 `userId`로 걸러진다. 관리자도 다른 사용자의 데이터를 볼 수 없다
- 비밀값(`DATABASE_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `BETTER_AUTH_SECRET`)은 환경 변수로만 다루고 저장소에 넣지 않는다. `.env*`는 `.env.example`만 커밋한다
- 연락처(전화번호, 주소, 생년월일)는 다른 데이터와 분리된 테이블에 둔다
- 테이블은 모듈이 소유한다. 정의는 `src/modules/<모듈>/schema.ts`에, 이름은 `<모듈>_<이름>`으로 짓는다. `src/db/schema.ts`는 각 모듈의 `schema.ts`를 모아 다시 내보내기만 한다. 다른 모듈의 테이블을 쿼리에 직접 쓰지 않는다(예외: `auth_user(id)`를 가리키는 외래 키)
- 라이브러리는 설치 시점의 최신 안정 버전을 쓴다. Better Auth와 Next.js는 최근 버전에서 API가 바뀌었으므로, 각 작업을 시작할 때 context7로 설치된 버전의 문서를 확인하고 이 계획의 이름과 다르면 문서를 따른다 (예: Next.js의 `middleware.ts`는 `proxy.ts`로 바뀌었다)
- 커밋과 배포는 사용자 확인을 받은 뒤에 한다

## Review Focus

1. 이메일 대소문자·앞뒤 공백 차이: `Hong@Gmail.com `을 허용 목록에 넣고 `hong@gmail.com`으로 로그인하면 들어와져야 한다 → 작업 3

# 데이터 접근 규칙

1. DB는 `src/modules/<모듈>/repo.ts`의 함수로만 읽고 쓴다. 페이지와 서버 액션에서 `db`를 직접 쓰지 않는다.

4. 사용자 데이터 테이블은 `auth_user(id)`를 `on delete cascade`로 참조하고, repo마다 "다른 사용자의 것은 읽히지 않는다" 테스트를 둔다.
5. 테이블은 모듈이 소유한다. 정의는 `src/modules/<모듈>/schema.ts`, 이름은 `<모듈>_<이름>`. 새 모듈을 만들면 `src/db/schema.ts`에 한 줄 추가한다.
6. 다른 모듈의 테이블을 직접 조회하지 않는다. 필요한 데이터는 그 모듈의 함수로 얻는다. 예외는 `auth_user(id)`를 가리키는 외래 키뿐이다.
