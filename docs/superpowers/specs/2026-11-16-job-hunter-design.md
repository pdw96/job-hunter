# Job Hunter 설계 문서 (1단계)

작성일: 2026-11-16
상태: 승인 대기

표기: 「결정」은 사용자가 대화에서 정한 것, 「제안」은 작성자(Claude)가 채운 것으로 사용자가 바꿀 수 있다.

---

## 1. 의도와 이유

일반 AI에게 이력서·자기소개서를 써 달라고 하면 그럴듯한 글은 나오지만, 지원자의 실제 경험이 제대로 살아 있지 않다. 원인은 AI가 지원자의 구체적인 경험(상황, 본인이 한 일, 수준, 수치)을 모르기 때문이다.

이 앱은 순서를 뒤집는다. 먼저 커리어를 검증된 기록으로 쌓고, AI는 그 기록만 근거로 지원서를 쓴다. 사용자는 어떤 경험이 왜 쓰였는지 쓰기 전과 후에 모두 확인할 수 있다.

사용자는 지금 같은 규칙을 Notion에서 손으로 운영하고 있다(이력 마스터, 검증 상태, 사용 금지 표현, 공고 채점 루브릭, 회사별 트래커). 이 앱은 그 운영 방식을 본인과 지인이 함께 쓸 수 있는 형태로 옮기는 것이다.

이 문서에서 "Notion을 따름"이라고 적은 곳은 구조와 원칙을 참고했다는 뜻이다. 필요한 내용은 모두 이 문서에 적었으며, Notion의 점수와 같은 결과가 나와야 하는 것은 아니다.

## 2. 목표, 비목표, 반목표

### 목표 (1단계)

1. 구글 로그인, 허용된 이메일만 가입
2. 첫 로그인 설문으로 트랙·희망 조건·채점 기준 생성
3. 경험 기록 쌓기: 기존 자료 가져오기 + AI 인터뷰 + 검증 루브릭
4. 붙여 넣은 공고의 적합도 채점과 지원 판단
5. 기록만 근거로 이력서와 자소서 문항별 답변 작성
6. 공통본 → 맞춤본 → 제출본 보존
7. 워드·PDF 내려받기
8. 지원 현황 관리
9. AI 사용량 한도와 개인 키 등록

### 비목표 (이번에 만들지 않음)

- 채용 사이트에서 공고를 자동으로 수집·추천 (2단계)
- 회사별 면접 준비, 결과 회고 (3단계)
- 증빙 서류와 이력서 대조 체크리스트 (1단계는 검증 상태와 메모로 대신)
- 누구나 가입하는 공개 서비스, 결제
- 다른 사용자의 기록 열람·공유
- 사용자가 올린 자기 양식 파일에 채워 넣기
- 채점 배점 숫자를 직접 편집하는 화면
- 지원서 자동 제출, 메일 발송

### 반목표 (동작하더라도 이러면 실패)

- 기록에 없는 경험·수치·역할을 지어내서 쓴다
- 「하지 않은 것」이나 승인된 금지 표현을 어긴 문장이 나온다
- 그럴듯하지만 어떤 경험에서 나왔는지 알 수 없는 문장이 나온다
- 한 사용자의 기록이 다른 사용자에게 보인다

## 3. 제약

- 「결정」 데이터베이스는 Neon(Postgres), 배포는 Vercel
- 「결정」 로그인은 구글 로그인
- 「결정」 사용 규모는 본인과 지인 몇 명
- 사용자의 이력과 연락처를 보관하므로 개인정보 보호가 필수
- 프로젝트 폴더는 비어 있고 git 저장소가 아니다

## 4. 접근 방식

갈리는 지점은 AI가 지원서를 쓸 때 경험 기록을 어떻게 건네받느냐였다.

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 1. 전부 건네기 | 트랙의 확인된 경험을 모두 주고 한 번에 작성 | 가장 단순 | 어떤 경험을 왜 골랐는지 사용자가 끼어들 수 없음 |
| 2. 고르기 → 쓰기 | AI가 문항별로 쓸 경험을 고르고 근거를 보여 줌. 사용자가 승인·변경한 뒤 그 경험만으로 작성 | 사용자가 쓰기 전에 통제. 문장별 근거 표시가 자연스러움. 문항 간 경험 중복 방지 | 단계가 하나 더 있고 만들 것이 많음 |
| 3. 의미 검색 | 경험을 검색용 데이터로 바꿔 공고와 비슷한 것만 건넴 | 경험이 수백 개여도 동작 | 개인 경력은 수십 개라 불필요. 검색이 놓친 경험을 AI가 못 봄 |

「결정」 **방식 2**를 쓴다. 이 앱의 목적이 "내 경험이 살았는지 내가 확인하는 것"이기 때문이다. 추가로 AI가 고른 경험마다 **추천 근거**를 보여 준다(6.5 참조).

## 5. 기술 선택

모두 「제안」이다.

- 화면과 서버: Next.js(App Router) + TypeScript
- 데이터: Neon Postgres. 스키마 관리 도구는 빌더가 정한다
- 로그인: 구글 OAuth. 라이브러리는 빌더가 정한다
- AI: Claude API. 모델은 계획 단계에서 품질과 비용을 보고 정한다
- 배포: Vercel
- 화면 언어: 한국어

## 6. 기능 설계

### 6.1 접근과 사용자

- 「결정」 구글 로그인만 지원한다
- 「결정」 관리자가 허용한 이메일만 가입된다. 관리자는 관리 화면에서 이메일을 추가·삭제한다
- 「제안」 최초 관리자는 환경 변수에 적은 이메일 한 개다
- 「제안」 허용 목록에 없는 계정으로 로그인하면 "초대받은 사람만 쓸 수 있습니다" 안내만 보이고 아무 데이터도 만들어지지 않는다
- 「제안」 모든 데이터는 소유 사용자에게 묶이고, 모든 조회·수정은 로그인한 사용자 기준으로 걸러진다. 관리자도 다른 사용자의 경험 기록과 지원서는 볼 수 없다. 관리자가 보는 것은 허용 이메일 목록과 사용자별 AI 사용량뿐이다

### 6.2 첫 로그인 설문과 트랙

「결정」 처음 로그인하면 설문을 진행하고, 답변으로 첫 트랙과 그 트랙의 희망 조건·제외 조건·채점 배점이 자동으로 만들어진다.

**분야와 직무 선택**

- 「결정」 분류는 NCS(국가직무능력표준)를 쓴다
- 「결정」 단계별 선택(대분류 → 중분류 → 직무)과 검색 둘 다 지원한다. 검색 결과를 고르면 상위 분류가 자동으로 채워진다
- 「결정」 앞 단계 선택에 따라 다음 단계 목록이 바뀐다
- 「제안」 직무는 여러 개 고를 수 있다
- 「제안」 NCS에 없는 흔한 이름(예: 백엔드, PM, MD)으로도 검색되도록 별칭을 붙인다. 그래도 없으면 직접 입력한다
- 확인됨(2026-11-16): 공공데이터포털의 NCS 분류 파일을 쓴다. 이용허락범위 제한 없음, 무료. 출처와 가공 방법은 `data/ncs/README.md`. 설계의 "직무"는 NCS의 세분류(867개)다

**설문 문항** (「결정」 큰 틀, 「제안」 세부 문구)

1. 분야와 직무
2. 지원 유형: 신입 / 경력 / 인턴 / 무관
3. 해당 분야에서 일한 기간
4. 근무 가능 지역 (선호 순서)
5. 희망 연봉, 고용 형태
6. 중요도 순서: 직무 일치, 근무지, 경력 요건, 분야, 우대 요건

**의존 동작** (「결정」 원칙, 「제안」 구체 예시)

| 앞의 답 | 달라지는 것 |
|---|---|
| 지원 유형 = 신입 | 3번을 건너뛰고, 채점의 경력 요건을 "신입 가능 여부"로 바꿈 |
| 지원 유형 = 경력 | 3번을 묻고 공고의 요구 경력과 비교 |
| 대분류에 따라 | 분야별 추가 질문 (예: 제조 계열은 교대·야간 근무 가능 여부, IT 계열은 재택 희망 여부) |
| 고른 직무 | 경험 인터뷰의 질문과 채점의 "직무 일치" 기준 |

분야별 추가 질문은 대분류에 붙인 데이터로 관리한다. 초기 목록의 구체 내용은 빌더가 정한다.

**트랙**

- 「결정」 구조: 트랙 → 회사 → 직무·공고 → 지원 회차
- 「결정」 희망 조건은 트랙마다 따로 둔다
- 「결정」 트랙을 추가할 때 같은 설문을 다시 한다
- 「결정」 채점 기준은 설정 화면에서 설문을 다시 여는 방식으로 고친다. 배점 숫자 직접 편집은 없다
- 「제안」 설문 직후 경험 기록 화면(가져오기 또는 인터뷰)으로 이어진다

### 6.3 경험 기록

**기록 한 건에 담는 것** (「제안」, Notion 마스터의 구조를 따름)

- 이름, 구분(재직 / 프로젝트 / 교육 / 학력 / 자격 / 공백 / 기타), 소속·기관, 직무·역할, 기간(월 단위)
- 내용: 상황, 본인이 한 일, 결과 (STAR 형태)
- 수치와 그 기준·산출 근거
- 하지 않은 것
- 쓰면 안 되는 표현
- 증빙·확인 메모
- 태그
- 트랙별 사용 범위: 사용 / 요약만 / 제외. 여러 트랙에 동시에 붙일 수 있다 (「결정」)
  - 「제안」 사용: 이력서와 자소서 모두에 쓴다
  - 「제안」 요약만: 이력서에 한두 줄로만 들어간다. 자소서 고르기 단계의 후보에는 나오지 않는다. 맞춤본에서 사용자가 직접 올리는 것은 가능하다. 적합도 채점의 근거로는 쓴다
  - 「제안」 제외: 그 트랙의 어디에도 쓰지 않는다
- 검증 루브릭 결과와 검증 상태

**쌓는 방법**

- 「결정」 중심은 AI 인터뷰다. AI가 질문하고 답변을 기록으로 정리한다
- 「결정」 기존 자료 가져오기: 글 붙여 넣기, PDF 파일, 워드 파일. AI가 경험 단위로 쪼개 초안을 만든다
- 「결정」 흐름은 가져오기 → 루브릭 채점 → 부족한 부분만 인터뷰. 자료가 없으면 바로 인터뷰
- 「결정」 가져온 초안은 원본에 무엇이 적혀 있었든 모두 미확인으로 시작한다. Notion 등 기존 도구의 검증 상태나 지원 기록을 그대로 옮기는 기능은 만들지 않는다
- 「제안」 가져온 글은 AI에 보내기 전에 전화번호·이메일·주민등록번호·상세 주소 형태를 코드로 가린다. 완벽하지 않으므로 가져오기 화면에 "연락처는 지우고 올리는 것이 안전합니다"라고 알린다. 원본 파일은 추출이 끝나면 보관하지 않는다
- 「제안」 저장된 기록은 사용자가 직접 고칠 수 있다. 내용을 고치면 루브릭을 다시 채점하고 본인 확인은 풀린다

**가져온 자료는 주장으로 다룬다** (「결정」 2026-11-17)

사용자의 기존 경력 자료는 AI로 작성된 것이다. 실제보다 부풀려진 표현이나 근거 없는 수치가 섞여 있을 수 있으므로, 가져온 내용을 사실로 취급하지 않는다.

- 가져온 기록마다 AI가 핵심 주장(역할 표현, 수치, 기간)을 뽑아 하나씩 묻고, 사용자는 타이핑 없이 버튼으로 답한다: 맞음 / 과장임 / 숫자 모름 / 틀림 / 고칠게요
- "과장임"은 그 표현을 금지 표현 후보로 보내고 문장에서 뺀다. "숫자 모름"은 그 수치를 닫아 수치 없이 서술하게 한다
- 기록 전체를 한 번에 "맞습니다"로 확인하는 것만으로는 가져온 기록이 확인됨이 되지 않는다. 주장별 확인을 마쳐야 한다
- 3-3번 계획에서 구체화한다

**검증 루브릭** (「결정」)

| 항목 | 확인하는 것 |
|---|---|
| 기간 | 시작과 끝이 월 단위로 적혀 있는가 |
| 본인 역할 | 본인이 한 일과 팀·타 부서가 한 일이 구분되어 있는가 |
| 수준 | 어느 수준까지 했는지, 하지 않은 것이 무엇인지 적혀 있는가 |
| 수치 | 수치가 있다면 기준과 산출 근거가 적혀 있는가 |
| 증빙 | 뒷받침할 서류나 자료가 있는가 |

- 「결정」 AI가 항목마다 충족 / 미달을 판정한다
- 「결정」 미달 항목마다 보완 방안(무엇을 알려 주면 채워지는지)을 보여 준다
- 「결정」 "지금 보완하기"를 누르면 AI가 미달 항목만 다시 질문한다
- 「결정」 보완할 수 없는 항목은 사용자가 "해당 없음"으로 닫을 수 있다. 그러면 그 내용만 지원서에서 빠진다 (예: 수치를 닫으면 수치 없이 서술)
- 「결정」 당장 채울 수 없는 증빙은 할 일 목록에 쌓인다
- 「결정」 AI는 기록이 구체적인지만 판정한다. 사실인지는 사용자가 "맞다"고 확인한다

**검증 상태** (「결정」 3단계, 「제안」 계산 규칙)

- 미확인: 사용자가 아직 확인하지 않음. AI가 만든 초안의 기본값
- 부분 확인: 사용자가 확인했지만 기간·본인 역할·수준 중 미달이 남아 있음
- 확인됨: 사용자가 확인했고 기간·본인 역할·수준이 충족됨
- 「제안」 수치와 증빙은 확인됨을 막지 않는다. 수치가 미달이거나 닫혀 있으면 그 수치만 지원서에서 빠지고, 증빙 미달은 할 일로 남는다
- 「제안」 구분에 따라 적용 항목이 다르다. 재직·프로젝트·교육·기타는 기간·본인 역할·수준이 필수다. 학력·자격·공백은 기간만 필수이고 본인 역할·수준은 처음부터 적용하지 않는다(자격은 취득일 하나로 기간을 충족)
- 「제안」 사용자가 "해당 없음"으로 닫을 수 있는 것은 수치와 증빙뿐이다. 필수 항목은 닫을 수 없고, 미달이면 부분 확인에 머문다
- 「결정」 지원서에는 확인됨만 쓴다
- 「제안」 적합도 채점은 확인됨과 부분 확인을 근거로 쓴다 (Notion 루브릭과 동일)

**하지 않은 것과 금지 표현** (「결정」)

- 경험마다 "하지 않은 것"과 "쓰면 안 되는 표현"을 둔다
- AI는 금지 표현을 스스로 확정하지 않는다. "하지 않은 것"을 보고 과장으로 읽힐 수 있는 표현을 후보로 제안하고, 사용자가 승인한 것만 금지 목록에 들어간다
- AI는 지원서를 쓸 때 두 칸을 금지 목록으로 쓴다

### 6.4 공고와 적합도 판단

- 「결정」 1단계에서는 사용자가 공고 원문을 붙여 넣는다
- 「제안」 공고를 넣을 때 트랙을 고르고, AI가 원문에서 회사명·직무명·마감일·근무지·요구 경력·고용 형태를 뽑아 채운다. 사용자가 고칠 수 있다
- 「결정」 공고 원문 전체를 보존한다
- 「결정」 지원서를 쓰기 전에 채점한다

**제외 조건** (점수 이전, 「제안」 구체 목록)

- 마감일이 지남
- 요구 경력이 설문의 경력보다 크게 높음
- 근무지가 희망 지역 밖
- 고용 형태가 희망과 다름
- 제외 조건에 걸려도 사용자가 무시하고 진행할 수 있다. 걸린 사유를 보여 준다

**점수** (「결정」 항목 고정, 배점은 설문에서 자동 생성)

- 항목: 직무 일치, 경력 요건, 분야 인접성, 근무지, 우대 요건
- 합계 100점. 설문 6번의 중요도 순서가 배점이 된다. 순서를 배점으로 바꾸는 식은 빌더가 정한다
- 추천 근거: 공고의 어느 문구가 기록의 어느 경험과 겹치는지만 쓴다. 기록에 없는 것은 쓰지 않는다
- 부족한 점: 요건 대비 실제로 모자란 것을 그대로 쓴다
- 「제안」 수치는 점수 근거로 인용하지 않는다 (Notion 루브릭과 동일)

**배점표를 다루는 방향** (「결정」 2026-11-17, 4번 계획에서 구체화)

서류 합불만으로는 배점을 통계로 맞출 수 없다(지원 건수가 적고, 경쟁률·시기 같은 요인이 섞인다). 그래서 다음을 따른다.

- 점수는 "붙을 확률"이 아니라 어느 공고에 시간을 쓸지 정하는 순서표다. 배점은 사용자의 우선순위다
- 점수를 둘로 나눈다. **원하는 정도**(근무지, 고용 형태, 분야)와 **자격이 맞는 정도**(직무 일치, 경력 요건, 우대 요건). 서류 결과는 두 번째에만 관련이 있다
- 회사별 인재상은 배점표에 넣지 않는다. 공고(와 사용자가 붙여 넣은 인재상 글)에서 AI가 요구 사항 목록을 뽑고, 확인된 경험이 그중 무엇을 덮는지로 본다
- 지원할 때의 점수와 배점을 그대로 저장한다. 나중에 배점을 바꿔도 과거 기록은 바뀌지 않는다
- 배점을 자동으로 고치지 않는다. 서류 결과가 쌓이면(10건 안팎) 점수 구간별·항목별로 결과를 표로 보여 주고, 바꿀지는 사용자가 정한다
- 위 "합계 100점, 다섯 항목" 구성은 이 방향에 맞게 4번 계획에서 다시 정한다

**지원 판단**

- 「결정」 사용자가 지원 / 보류 / 제외를 고른다. 지원을 골라야 작성으로 넘어간다
- 「제안」 같은 회사·직무의 기존 기록이 있으면 보여 주고, 재지원은 지원 회차로 누적한다

### 6.5 지원서 작성

**입력**

- 공고(6.4에서 지원으로 판단한 것)
- 자소서 문항: 문항 글, 글자 수 제한, 제한 기준(공백 포함 / 제외) (「결정」)

**고르기 단계** (「결정」)

- AI가 문항마다 쓸 경험을 고르고 후보도 함께 보여 준다
- 고른 경험마다 추천 근거를 보여 준다. 근거에는 다음을 담는다 (「제안」 구성)
  - 문항이나 공고의 어느 문구와 겹치는가
  - 그 경험에서 쓸 수 있는 것: 확인된 수치가 있는지, 본인 역할이 무엇인지
  - 후보로 밀린 경험은 왜 밀렸는가
- 사용자가 경험을 바꾸거나 승인한다
- 「제안」 같은 경험이 여러 문항에 겹치면 표시해서 알려 준다. 막지는 않는다
- 「제안」 쓸 만한 경험이 없으면 고르지 않고 "이 문항에 맞는 확인된 기록이 없습니다"라고 알리고, 경험 인터뷰로 가는 길을 제시한다

**쓰기 단계**

- 「결정」 승인된 경험만 가지고 쓴다
- 「결정」 기록에 없는 경험·수치·역할은 쓰지 않는다. 근거가 부족하면 메우지 않고 부족하다고 알린다
- 「결정」 문장(또는 문단)마다 어떤 경험에서 나왔는지 볼 수 있다
- 「결정」 "하지 않은 것"과 금지 표현을 지킨다
- 「제안」 작성 후 금지 표현과 글자 수 제한을 코드로 한 번 더 검사하고, 어긴 곳은 표시한다
- 「결정」 사용자가 직접 고칠 수 있고, AI에게 부분 수정을 요청할 수 있다. 부분 수정도 같은 규칙을 따른다
- 「제안」 사용자가 직접 고친 문장은 근거 표시가 "직접 수정"으로 바뀐다

**이력서**

- 「결정」 트랙마다 공통본을 둔다. 확인된 경험 중 그 트랙에서 사용 / 요약만인 것으로 AI가 만들고 사용자가 다듬는다
- 「결정」 맞춤본은 공통본에서 출발해 공고에 맞게 고친다
- 「제안」 맞춤본에서도 고르기 단계를 거친다. AI가 강조할 경험과 순서를 근거와 함께 제안하고 사용자가 승인한다

**제출본 보존** (「결정」)

- "제출함"을 누르면 그 시점의 이력서, 자소서, 공고 원문이 얼려진다
- 이후 경험 기록을 고쳐도 제출본은 바뀌지 않는다
- 「제안」 제출 후 고치려면 새 버전을 만든다

### 6.6 내려받기

- 「결정」 워드(DOCX)와 PDF. 기본은 워드
- 「결정」 파일 이름은 영문·숫자·밑줄만
- 「결정」 이력서 양식은 국문 기본형, 영문형, 경력기술서형 중 선택
- 「제안」 영문형은 한국어 기록을 영어로 옮겨 쓴다. 번역은 지어내기가 아니지만, 같은 금지 규칙을 적용한다
- 「결정」 자소서는 문항마다 복사 버튼과 글자 수(공백 포함 / 제외)를 표시한다
- 「결정」 연락처(전화번호, 주소, 생년월일 등)는 경험 기록과 분리해 보관하고 파일을 만들 때만 넣는다
- 「제안」 연락처는 AI에게 보내지 않는다

### 6.7 지원 현황

「결정」 가볍게 포함한다. 「제안」 세부는 Notion 트래커를 따른다.

- 회사별로 직무·지원 회차를 묶어 보여 준다
- 지원 건마다: 지원 판단, 진행 상태(관심 / 검토중 / 서류작성 / 지원완료 / 인적성·AI면접 / 코딩테스트 / 1차면접 / 2차·최종면접 / 최종합격 / 불합격 / 지원철회), 적합도, 마감일, 다음 행동, 다음 일정, 지원 경로, 메모
- 진행 중인데 다음 행동과 다음 일정이 비어 있는 건을 눈에 띄게 표시한다

### 6.8 AI 비용

- 「결정」 기본은 관리자의 키로 쓰고 1인당 월 한도를 둔다
- 「결정」 자기 키를 등록한 사용자는 한도 없이 쓴다
- 「제안」 한도는 월 사용 금액 기준이고 관리자가 기본값을 정한다. 초기 기본값은 계획 단계에서 모델 가격을 보고 제안한다
- 「제안」 한도에 닿으면 AI 기능만 멈추고, 기록 조회·수정·내려받기는 계속 된다. 남은 한도를 화면에 보여 준다
- 「제안」 등록된 키는 암호화해서 저장하고, 등록 후에는 화면에 다시 보여 주지 않는다

## 7. 개인정보

- 사용자 간 데이터 격리 (6.1)
- 연락처 분리 보관, AI에 보내지 않음 (6.6)
- 개인 키 암호화 (6.8)
- 「제안」 사용자가 자기 데이터 전체를 삭제할 수 있다
- 「제안」 비밀값(구글 OAuth, DB 접속 정보, AI 키, 암호화 키)은 환경 변수로만 다루고 저장소에 넣지 않는다

## 8. 만드는 순서 (「제안」)

각 단계가 끝나면 그 자체로 써 볼 수 있다.

1. 기반: 프로젝트 생성, 구글 로그인, 허용 이메일, 사용자 격리
2. 설문과 트랙: NCS 분류, 검색, 의존 동작, 트랙·희망 조건·채점 기준 생성
3. 경험 기록: 직접 입력과 수정, AI 인터뷰, 검증 루브릭, 보완, 금지 표현
4. 가져오기: 붙여 넣기, PDF, 워드
5. 공고와 적합도: 붙여 넣기, 제외 조건, 채점, 지원 판단
6. 지원서 작성: 고르기 → 쓰기, 근거 표시, 부분 수정
7. 이력서: 공통본, 맞춤본, 제출본 보존
8. 내려받기: 양식 3종, 워드, PDF
9. 지원 현황
10. AI 사용량 한도, 개인 키

## 9. 빌더에게 맡기는 것

- 데이터 구조(테이블과 관계)의 세부
- 화면 구성과 디자인
- 라이브러리 선택(로그인, 스키마 관리, 문서 생성, 파일 읽기)
- AI 프롬프트의 문구, 고르기·쓰기·채점·루브릭 판정 각각의 호출 구성
- 순서를 배점으로 바꾸는 식, 제외 조건의 구체 기준값
- 분야별 추가 질문과 별칭의 초기 목록
- 테스트 방식. 단, 반목표 네 가지는 자동 테스트로 확인할 수 있어야 한다

## 10. 이후 단계

- 2단계 공고 추천: 사용자는 이미 매일 공고를 수집·채점해 Notion에 쌓는 예약 작업을 돌리고 있다. 2단계는 그 작업을 앱으로 옮기는 일이며 별도로 설계한다
- 3단계 면접 준비와 회고: 회사별 면접 준비, 실제 질문, 결과와 원인 가설, 기록 반영
