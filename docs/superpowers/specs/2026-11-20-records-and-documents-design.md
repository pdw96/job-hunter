# 경험 기록 개편과 공고별 서류 작성 설계

작성일: 2026-11-20
상태: 승인됨 (2026-11-20, 예시 화면을 보고 승인)
바꾸는 곳: 1단계 설계(`2026-11-16-job-hunter-design.md`)의 6.3 경험 기록, 6.4 공고(제출 서류·회사 조사 추가), 6.5 지원서 작성(자유양식·문항 유형·경력기술서 추가). 이 문서와 1단계 설계가 다르면 이 문서를 따른다.

표기: 「결정」은 사용자가 대화에서 정한 것, 「제안」은 작성자(Claude)가 채운 것으로 사용자가 바꿀 수 있다.

## 1. 의도와 이유

사용자가 실제 공고로 자소서를 받아 보고 마음에 들어 하지 않았다(2026-11-20). 원인으로 본 것:

- 경험 기록은 구분(재직·프로젝트·교육·학력·자격·공백·기타)이 7가지여도 모두 같은 칸(상황·한 일·결과·수치)과 같은 루브릭을 쓴다. 학력에도 "상황·결과"를 묻고, 학력이 자소서 후보로 추천됐다(PR #35에서 학력·자격을 자소서 후보에서 빼는 것만 먼저 고쳤다).
- 재직 하나가 기록 하나라서, 자소서에 쓸 구체적인 장면을 꺼내기 어렵다.
- 지원동기·입사 후 포부·성장과정 같은 문항의 재료(왜 이 회사인가, 목표, 가치관)를 적을 자리가 없다. 회사에 대한 정보도 사용자가 붙여 넣은 인재상 글뿐이다.
- 회사마다 내라는 서류와 자소서 문항이 다르다. 문항을 주지 않는 회사(자유양식)도 있다.
- 운영 DB를 보면 사용자의 기록 37개가 모두 노션 가져오기로 들어왔고, 확인됨은 3개(프로젝트 1, 자격 1, 학력 1)다. 자소서에 쓸 수 있는 장면이 사실상 프로젝트 하나였다.

사용자가 원하는 것(「결정」): **공고가 뜨면, 공고 내용과 경험 기록을 맞대서 그 공고가 요구하는 서류(이력서, 경력기술서, 자기소개서)를 써 준다.** 그러려면 기록을 메뉴별로 나눠 메뉴마다 맞는 칸으로 관리하고, 기록에 없는 재료는 그때그때 묻고, 회사 정보는 찾아와야 한다.

## 2. 목표, 비목표, 반목표

### 목표

1. 경험 기록을 메뉴로 나눈다: 기본정보 / 학력 / 경력 / 자격·어학·수상 / 경험 사례. 메뉴마다 맞는 칸과 확인 방식을 둔다
2. 지금 기록 37개를 새 구조로 옮긴다
3. 공고에서 제출 서류와 자소서 문항을 읽는다. 문항이 없으면 자유양식 항목을 체크박스로 고른다
4. 자소서 문항을 유형(경험형·동기포부형·자기소개형)으로 나눠 유형마다 다른 재료를 쓴다
5. 기록에 없는 재료(지원동기, 포부, 성장과정 등)는 작성할 때 AI가 짧게 묻고, 답을 다음 공고에서 다시 쓴다
6. `지원`으로 정한 공고의 회사를 Claude 웹 검색으로 조사해 인재상과 최근 소식을 출처와 함께 보여 주고, 사용자가 고른 것만 쓴다
7. 경력기술서를 AI가 쓰는 서류로 추가한다

### 비목표 (이번에 만들지 않음)

- 「결정」 포트폴리오 작성. 이번에는 "직접 준비" 서류로만 보여 준다. 나중에 AI가 쓰는 서류로 바꿀 수 있게 서류 종류를 목록으로 둔다(5.3)
- 「결정」 동기·목표를 미리 적어 두는 메뉴. 필요할 때 묻는다(5.6)
- 내려받기(6번 계획). 이 설계는 6번이 쓸 내용(이력서·경력기술서·자소서)의 모양만 정한다
- 회사 조사 결과로 이미 매긴 공고 점수를 다시 매기는 것
- 증명서(졸업·성적·자격) 파일 보관

### 반목표 (동작하더라도 이러면 실패)

- 1단계 설계의 반목표는 그대로다(지어내기, 금지 표현 어기기, 출처 모를 문장, 다른 사용자에게 보임)
- 회사 정보를 지어내거나, 출처에 없는 내용을 회사 정보로 쓴다
- 회사 정보나 공고 문구를 지원자가 한 일처럼 섞어 쓴다
- 지원자가 답하지 않은 동기·포부·가치관을 AI가 지어 쓴다
- 학력·자격 같은 이력 사실이 자소서 경험형 문항의 근거로 나온다
- 옮기는 중에 사용자의 기록이 사라지거나, 개편 중간에 자소서·이력서·채점이 멈춘다

## 3. 제약

- 1단계 설계와 `CLAUDE.md`의 규칙을 따른다: AI 호출은 `runAi()`, 모델은 `claude-sonnet-5-5`, 연락처는 AI에 보내지 않음, 가져온 자료는 확인이 필요한 주장, 테이블은 모듈이 갖고 이름은 `<모듈>_<이름>`
- 「결정」 서비스는 개편 중에도 계속 돌아가야 한다. 단계별로 나눠 합친다
- 운영 DB에 실제 사용자 기록이 있다(위 37개). 옛 표를 지우는 것은 판단표 ②의 "반드시 묻기"다
- 사용자는 타자를 싫어한다. 묻기는 버튼·선택지를 먼저 쓰고, 글은 짧게 받는다

## 4. 접근 방식

갈린 지점은 경험 기록을 DB에 어떻게 나눠 담느냐였다. 화면에서 보이는 것(메뉴별 칸, 확인 방식)은 세 방법 모두 같다.

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 리모델링 | 지금 기록 표를 "장면"으로 살리고, 이력 사실만 새 표로 | 만들 것이 적고 지금 기능이 덜 깨진다 | 장면 표에 예전 칸 이름이 남는다. 메뉴와 표가 어긋난다 |
| B. 재건축 | 메뉴마다 표를 새로 만들고, 옛 표는 옮긴 뒤 없앤다 | 메뉴와 표가 1:1. 6·7번 계획을 그 위에 쌓기 쉽다 | 자소서·이력서·제출본·주장 확인·채점을 새 표에 다시 이어야 해서 만들 것과 깨질 곳이 많다 |
| C. 칸만 더함 | 지금 표 하나에 구분별 칸과 부모 칸을 더한다 | 가장 빠르다 | 학력에도 상황·결과 칸이 남아 "메뉴마다 맞는 칸" 결정과 어긋난다 |

「결정」 **방법 B**. 작성자는 A를 추천했지만, 사용자는 오래 쓸 구조를 위해 시간이 더 들어도 B가 낫다고 정했다. 6·7번 계획이 이 구조 위에 쌓인다. 대신 단계별로 나눠 합쳐 그동안에도 서비스가 돌게 한다(9장).

## 5. 기능 설계

### 5.1 메뉴와 칸

「결정」 메뉴로 나누고, 메뉴마다 맞는 칸을 둔다. 메뉴 구성은 아래와 같다(작성자가 제안하고 사용자가 받아들였다).

```
경험 기록 ▾
├ 기본정보        이름·연락처·생년월일·주소 (지금 '내 정보'. AI에 안 보냄)
├ 학력            학교 / 교육 과정
├ 경력            회사 / 공백 기간
├ 자격·어학·수상
└ 경험 사례       경력·프로젝트·활동 아래 장면 여러 개
```

칸은 모두 「제안」이다. 빌더가 화면을 만들며 조정할 수 있지만, 이력 사실에 서술형 칸(상황·결과)을 두지 않는다는 원칙은 지킨다.

**기본정보**: 지금 `profile_contacts`와 같다(법적 이름, 전화, 주소, 생년월일, 연락용 이메일). 메뉴에서 그 화면으로 잇는다. 연락처 규칙(따로 저장, AI에 안 보냄)은 그대로다.

**학력**

| 칸 | 비고 |
|---|---|
| 학교 이름 | 필수 |
| 학위 구분 | 고등학교 / 전문학사 / 학사 / 석사 / 박사 |
| 전공 | 고등학교는 비워도 됨 |
| 입학 월, 졸업 월 | YYYY-MM. 재학 중이면 졸업 월 대신 상태 |
| 상태 | 졸업 / 졸업 예정 / 재학 / 휴학 / 수료 / 중퇴 |
| 학점 | 선택. 학점과 만점(4.5 / 4.3 / 4.0) |

**교육 과정**(학력 메뉴 안의 두 번째 구역): 과정 이름, 기관, 시작·끝 월, 교육 시간(선택), 배운 것 한두 줄(선택, 100자 안팎).

**경력**

| 칸 | 비고 |
|---|---|
| 회사 이름 | 필수 |
| 부서 | 선택 |
| 직급·직책 | 선택 |
| 고용 형태 | 정규직 / 계약직 / 인턴 / 프리랜서 / 아르바이트 |
| 입사 월, 퇴사 월 | 재직 중 표시 가능 |
| 담당 업무 | 짧은 줄 몇 개(줄마다 100자 안팎, 많아야 8줄). 이력서·경력기술서 머리에 쓴다 |

**공백 기간**(경력 메뉴 안에 시간 순으로 끼움): 시작·끝 월, 무엇을 했는지 한 줄(선택).

**자격·어학·수상**: 종류(자격증 / 어학 / 수상), 이름, 발급·주최 기관, 취득 월, 점수·등급(선택, 어학·수상에서 주로 씀).

**경험 사례**: 장면을 담는 머리 세 종류와 그 아래 장면이다.

- 머리
  - 경력: 위 경력 항목을 그대로 머리로 쓴다(따로 만들지 않는다)
  - 프로젝트: 이름, 소속(경력 하나에 딸리거나, 개인·학교·교육), 시작·끝 월, 역할, 쓴 기술·도구(선택), 한 줄 요약
  - 활동: 동아리·봉사·대외활동 등. 이름, 기관, 시작·끝 월, 역할
- 장면(경험 사례 하나)
  - 제목, 머리(경력·프로젝트·활동 중 하나, 필수), 기간(선택. 비우면 머리의 기간을 쓴다)
  - 상황, 판단(왜 그렇게 하기로 했나), 본인이 한 일, 결과, 배운 점
  - 수치와 그 기준, 하지 않은 것, 쓰면 안 되는 표현(승인한 것만), 증빙 메모, 태그
- 짧은 프로젝트는 장면이 하나여도 된다. 머리에 장면이 없어도 이력서·경력기술서에는 머리만으로 들어간다

**트랙별 사용 범위**(사용 / 요약만 / 제외): 「제안」 학력·교육·경력·공백·자격·머리·장면 모두에 둔다. 기본값은 사용. 뜻은 1단계 설계와 같다. 장면의 "요약만"은 자소서 후보에서 빠지고 이력서에는 한두 줄로 들어간다.

### 5.2 확인 방식

「제안」 이력 사실과 장면의 확인을 다르게 한다(대화에서 사용자에게 보였고 고칠 곳이 없다고 했다).

**이력 사실**(학력, 교육 과정, 경력, 공백, 자격·어학·수상, 프로젝트·활동 머리)

- 코드가 형식을 본다: 필수 칸, 월 형식, 끝이 시작보다 뒤인지
- 사용자가 `맞음`을 한 번 누르면 확인됨. 칸이 모두 화면에 보이는 짧은 항목이므로 `맞음` 한 번이 칸별 확인을 겸한다
- 상태는 미확인 / 확인됨 둘. 내용을 고치면 미확인으로 돌아간다
- AI 루브릭 판정을 하지 않는다
- 가져온 항목의 서술 칸(경력의 담당 업무 줄, 프로젝트 한 줄 요약)은 AI가 쓴 주장일 수 있다. 「제안」 이 줄들은 장면의 주장 확인과 같은 버튼(맞음 / 과장임 / 숫자 모름 / 틀림 / 고칠게요)으로 줄마다 확인해야 `맞음`을 누를 수 있다

**장면**

- 지금 루브릭과 검증 상태를 그대로 쓴다: 기간·본인 역할·수준 필수, 수치·증빙은 "해당 없음"으로 닫을 수 있음, 미확인 / 부분 확인 / 확인됨
- 기간은 장면에 비어 있으면 머리의 기간으로 판정한다
- 가져온 장면은 주장별 확인을 거친다(지금과 같다)
- 판단·배운 점은 루브릭 항목이 아니다. 비어 있어도 확인됨이 될 수 있다
- 「결정」 장면은 그 머리(경력·프로젝트·활동)도 확인됨이어야 지원서에 쓴다(2026-11-20). 확인하지 않은 회사 이름이나 기간이 글에 들어가지 않게 하기 위해서다. 장면을 확인하는 화면에서 머리가 미확인이면 "회사 정보도 맞나요? [맞음]"을 함께 보여 한 번에 누를 수 있게 한다. 자소서 고르기·이력서·경력기술서가 같은 거르기를 쓴다. 적합도 채점은 지금처럼 부분 확인까지 쓰므로 머리의 확인 여부를 따지지 않는다

**어디에 쓰나**: 「결정」 지원서에는 확인됨만 쓴다(이력 사실도 같다). 적합도 채점은 지금처럼 확인됨과 부분 확인 장면, 그리고 확인된 이력 사실을 근거로 쓴다.

### 5.3 공고에서 제출 서류와 문항 읽기

「결정」 공고에 제출 서류가 적혀 있으면 그것에 맞게 작성한다. 공고에 자소서 문항이 있으면 그 문항에, 없으면 자유양식으로 쓴다.

- 「제안」 공고를 읽을 때(붙여 넣기·주소·그림, 4-1의 값 뽑기) AI가 함께 뽑는다
  - 제출 서류 목록: 서류마다 종류와 공고에 적힌 이름. 종류는 이력서 / 자기소개서 / 경력기술서 / 포트폴리오 / 기타
  - 자소서 문항: 문항 글, 글자 수 제한, 공백 포함 여부(적혀 있을 때)
- 「제안」 서류가 공고에 없으면 이력서·자기소개서를 기본으로 고른다. 사용자가 체크로 더하거나 뺀다
- 「제안」 서류 종류마다 "AI가 씀 / 직접 준비"를 코드의 목록 하나로 정한다. 이번에는 이력서·자기소개서·경력기술서만 AI가 쓴다. 포트폴리오·기타는 "직접 준비" 목록에 이름만 보인다. 나중에 포트폴리오를 AI가 쓰게 바꿀 때 이 목록만 바꾸고 화면을 더하면 되게 만든다
- 「제안」 공고에서 뽑은 문항은 `지원`으로 정할 때 자소서 문항으로 채운다. 사용자가 고치거나 지울 수 있다. 이미 문항이 있는 공고에는 덮어쓰지 않는다
- 「제안」 이미 있는 공고에는 `다시 읽기`를 눌러야 서류·문항을 뽑는다(자동으로 다시 부르지 않는다)

```
공고 넣기 → AI가 공고에서 읽음
  제출 서류: 이력서 ✓  자기소개서 ✓  경력기술서 ✓  포트폴리오(직접 준비)
  자소서 문항: 공고에 있으면 채워 둠 / 없으면 자유양식 체크박스
→ 고른 서류마다 [작성]
```

### 5.4 자유양식 자기소개서

「결정」 문항이 없는 회사는 쓸 항목을 체크박스로 골라 작성한다.

```
자기소개서 ─ ( ) 문항 붙여 넣기   (•) 자유양식
  쓸 항목:  [x] 지원동기   [x] 직무 역량·경험   [ ] 성장과정
            [ ] 성격의 장단점   [x] 입사 후 포부   [ ] 가치관
            [+ 항목 직접 추가]
  항목당 글자 수: [ 800 ]                  [작성]
```

- 「제안」 항목 목록: 성장과정, 성격의 장단점, 지원동기, 직무 역량·경험, 입사 후 포부, 가치관·생활신조, 협업 경험, 어려움을 극복한 경험. 직접 추가는 짧은 글 한 줄
- 「제안」 고른 항목은 지금의 자소서 문항 한 줄씩으로 만든다(문항 글은 항목 이름, 글자 수는 항목당 글자 수). 이후 흐름(고르기 → 승인 → 쓰기 → 고치기 → 제출)은 문항과 같다
- 「제안」 글자 수는 항목마다 따로 고칠 수 있다

### 5.5 문항 유형과 재료

「제안」 문항마다 유형을 정해 다른 재료를 쓴다(대화의 이전 논의에서 정한 방향).

| 유형 | 예 | 재료 |
|---|---|---|
| 경험형 | 직무 역량·경험, 협업, 어려움 극복, 성과 | 확인된 장면(트랙에서 "사용"). 지금의 고르기 → 승인 → 쓰기 |
| 동기포부형 | 지원동기, 입사 후 포부 | 공고, 확인한 회사 조사(5.7), 지원자의 답(5.6), 이어지는 장면이 있으면 그 장면 |
| 자기소개형 | 성장과정, 성격의 장단점, 가치관 | 지원자의 답(5.6), 뒷받침할 장면이 있으면 그 장면 |

- 자유양식 항목은 유형이 정해져 있다(위 표). 공고 문항과 붙여 넣은 문항은 AI가 고르기 단계에서 유형을 붙이고, 화면에 보여 사용자가 바꿀 수 있다
- 한 문항이 여러 유형을 함께 물으면(예: "지원 동기와 직무 역량") 두 재료를 함께 쓴다
- 이력 사실(학력·자격 등)은 어느 유형의 근거로도 고르지 않는다. 다만 쓰기 단계에서 사실 확인용으로 보낼 수 있는지는 빌더가 정한다(예: "전공을 살려"를 쓰려면 전공이 필요하다). 보낸다면 확인된 것만 보내고 근거 표시는 하지 않는다

### 5.6 필요할 때 묻기

「결정」 동기·목표 메뉴는 두지 않는다. 작성할 때 모자란 항목만 AI가 짧게 묻는다.

- 동기포부형·자기소개형 문항을 쓰기 전에, 쓸 답이 없으면 AI가 그 공고·문항에 맞춰 질문을 2~3개 만든다
- 「제안」 질문마다 고를 수 있는 답 3~5개와 `기타 (짧게 적기)`를 준다. 사용자는 고르고, 필요하면 한 줄 덧붙인다. AI가 만든 선택지는 지원자의 말이 아니므로, 사용자가 고른 것만 답으로 저장한다
- 「제안」 답은 새 표에 저장한다. 답마다 주제(지원동기 / 입사 후 포부 / 성장과정 / 성격의 장단점 / 가치관 / 기타), 질문, 답, 회사에 묶인 답인지(지원동기처럼 그 회사에만 쓰는 답이면 공고 id)를 둔다
- 「제안」 다음 공고에서 같은 주제를 만나면 "지난번 답을 쓸까요?"로 보이고, `그대로 쓰기 / 고쳐 쓰기 / 새로 답하기`를 고른다. 회사에 묶인 답은 같은 회사 공고에서만 다시 보인다
- 사용자가 저장한 답은 사용자가 직접 한 말이므로 확인됨으로 본다. 쓰기 단계에서는 답에 적힌 것만 쓰고 넓히지 않는다. 답이 근거인 문단은 근거 표시에 "내 답: (주제)"로 보인다
- 지금 자소서 화면의 `AI 인터뷰로 추가`(경험 인터뷰로 가던 버튼)는 동기포부형·자기소개형 문항에서는 이 묻기로 바뀐다. 경험형 문항에서는 지금처럼 장면 인터뷰로 간다

### 5.7 회사 조사

「결정」 공고를 `지원`으로 정하면 Claude 웹 검색으로 인재상과 회사의 최근 소식을 찾는다. 출처와 함께 보여 주고, 사용자가 `맞음`·체크한 것만 쓴다.

```
회사 조사 ─ ○○전자                         조사일 2026-11-20 [다시 조사]
 인재상     "도전·협업·고객"            출처: ○○.com/careers     [맞음] [아님]
 최근 소식  [x] 3분기 영업이익 전년보다 늘어남   출처: △△일보 11/05
            [x] 북미 배터리 공장 착공            출처: □□뉴스 10/21
            [ ] 신임 대표 선임                   출처: ...
 → 체크한 것만 자소서(특히 지원동기·포부)에 씁니다
```

- 「결정」 `지원`으로 정할 때 자동으로 돌린다. 넘기는 공고에는 돈을 쓰지 않는다. `다시 조사` 버튼도 둔다
- 「결정」 웹 검색은 Claude API의 서버 도구(`web_search_20260209`)를 쓴다. 우리 서버는 페이지를 열지 않는다. 새 외부 서비스에 가입하지 않는다
- 「제안」 공고에 인재상이 이미 있으면(공고 원문이나 사용자가 붙여 넣은 인재상 글) 인재상은 찾지 않고 최근 소식만 찾는다
- 「제안」 공고에 회사 홈페이지 주소가 있으면 인재상 검색은 그 도메인으로 좁힌다(`allowed_domains`). 최근 소식은 좁히지 않는다
- 「제안」 소식마다 한두 줄 요약, 날짜, 출처 주소, 숫자가 있으면 그 숫자를 담는다. 코드가 출처 주소가 이번 검색 결과에 실제로 나온 주소인지 확인하고, 아니면 버린다. 날짜를 모르는 소식은 "날짜 모름"으로 보인다
- 「제안」 소식은 많아야 8개. 지원 동기에 쓸 만한 것(실적, 사업·제품, 투자·진출, 수상) 위주로, 사건·사고·소송 같은 것은 빼라고 지시한다
- 「제안」 조사 결과는 사용자·회사 단위로 저장하고, 같은 회사의 다른 공고에서 다시 쓴다. 회사가 같은지는 회사 이름을 정리한 값(공백·(주)·주식회사 등을 뺀 값)으로 본다. 90일이 지나면 "오래된 조사입니다"를 보이고 `다시 조사`를 권한다
- 「제안」 AI에게 보내는 것은 회사 이름, 공고 제목, 공고의 회사 주소뿐이다. 지원자 정보는 보내지 않는다
- 「제안」 검색이 실패하거나 조직 설정에서 웹 검색이 꺼져 있으면, "찾지 못했습니다. 인재상을 붙여 넣어 주세요"를 보이고 지금의 인재상 붙여 넣기 칸으로 잇는다
- 「제안」 비용: 검색 1,000번에 10달러와 읽은 글의 토큰. 지금 AI 사용량·월 한도에 함께 센다(검색 횟수 요금을 사용량 계산에 더한다). 한 번 조사에 검색은 많아야 5번(`max_uses`)
- 「결정」 외부 정보(회사 조사, 공고 읽기)가 틀렸을 때 그 비용을 사용자 한도에서 빼고 앱이 부담할지는 아직 정하지 않았다(2026-11-20). 버튼과 비용을 묶으면 장난으로 누를 수 있고, 항상 앱 부담으로 하면 상한이 필요해 불편해질 수 있어서다. 처음에는 지금처럼 사용자 한도에서 세고, 5-6 배포 뒤 실제 비용과 틀린 비율을 보고 7번 계획에서 정한다. 그때 쓸 수 있게 회사 조사·공고 읽기 비용은 사용량 기록에서 목적(`purpose`)으로 따로 구분되게 한다
- 쓰기 단계: 「제안」 확인한 인재상과 체크한 소식만 보낸다. 회사 정보는 회사 이야기에만 쓰고 지원자가 한 일처럼 쓰지 않는다. 회사 정보가 근거인 문단은 근거 표시에 "회사 정보: (출처)"로 보인다
- 숫자 검사: 「제안」 자소서의 "기록에 없는 숫자" 표시에서, 체크한 회사 소식의 숫자는 허용한다
- 규칙 변경: `CLAUDE.md`의 "주소로 공고를 읽는 기능은 사용자가 넣은 주소 하나만 연다"에 "회사 조사는 Claude 웹 검색을 쓰고, 우리 서버는 페이지를 열지 않는다"를 덧붙인다
- 사용자가 할 일: Anthropic 콘솔의 조직 설정에서 웹 검색이 꺼져 있으면 켠다. 빌더가 첫 배포 때 확인해 알린다

### 5.8 경력기술서

「결정」 AI가 쓰는 서류로 추가한다. 공고가 경력기술서를 요구하면(또는 사용자가 체크하면) 쓴다.

- 「제안」 모양(흔한 국문 양식): 회사마다 머리(회사, 부서, 직급, 기간, 담당 업무)를 코드가 이력 사실에서 채우고, 그 아래 프로젝트·업무마다 이름, 기간, 역할, 한 일, 성과(확인된 수치만), 쓴 기술을 AI가 확인된 장면으로 쓴다
- 「제안」 이력서와 같은 방식을 따른다: 트랙마다 공통본, 지원 공고마다 맞춤본(공고에 맞춰 강조할 프로젝트를 근거와 함께 고르고 사용자가 승인), 줄 고치기·순서·빼기·다시 쓰기, 같은 검사(금지 표현, 기록에 없는 숫자, 바뀐 기록 표시)
- 「제안」 경력이 없으면 "경력이 없어 경력기술서를 만들 수 없습니다"를 보인다. 프로젝트 기술서로 바꿔 쓰는 것은 이번에 하지 않는다
- 「제안」 제출본(5-3)에 경력기술서도 얼린다. 내려받기(6번)의 "경력기술서형" 양식은 이 내용을 쓴다

### 5.9 이력서와 채점이 새 구조를 쓰는 방식

- 이력서(5-2): 「제안」 학력·교육·자격·어학·수상 구역은 코드가 확인된 이력 사실로 채우고 AI를 부르지 않는다. 경력 구역은 머리(코드)와 담당 업무, 그 아래 장면에서 AI가 쓴 줄로 만든다. 프로젝트·활동도 머리와 장면 줄로 만든다. 공통본·맞춤본·강조 고르기·검사 방식은 그대로다
- 적합도 채점(4-2): 「제안」 요구 사항과 맞대는 재료에 확인된 이력 사실(학력, 자격, 경력 기간)을 더한다. "학사 이상", "정보처리기사" 같은 요건을 이력 사실로 덮을 수 있게 한다
- 자소서 고르기(5-1): 경험형은 장면만 후보로 쓴다(이력 사실은 후보가 아니다)

### 5.10 기존 기록 옮기기

「결정」 AI가 지금 기록을 새 메뉴로 옮긴다. 학력·자격은 칸에 맞춰 옮기고, 경력·프로젝트는 머리와 장면 초안으로 나눈다. 확인은 새로 한다.

- 「제안」 옮기는 방법

| 지금 구분 | 옮길 곳 |
|---|---|
| 학력 | 학력. 학교·전공·학위는 이름·소속·역할에서 AI가 나눠 채운다 |
| 교육 | 교육 과정 |
| 자격 | 자격·어학·수상(종류는 AI가 정함) |
| 공백 | 공백 기간 |
| 재직 | 경력(머리) + 장면 초안 여러 개(AI가 상황·한 일·결과를 장면 단위로 나눔) |
| 프로젝트 | 프로젝트 머리 + 장면 1개(내용을 칸에 그대로 옮김. 판단·배운 점은 비움) |
| 기타 | 활동 머리 + 장면 1개 |

- 「제안」 프로젝트가 재직 기간 안에 있고 소속이 같으면, AI가 그 경력에 딸린 프로젝트로 제안한다. 사용자가 화면에서 바꿀 수 있다
- 「결정」 옮긴 항목은 미확인으로 시작한다. 다만 내용을 그대로 옮긴 것은 확인 상태를 이어 간다(2026-11-20, 바꾼 날부터 쓸 기록이 0개가 되지 않게): 확인된 프로젝트는 장면의 칸에 글을 바꾸지 않고 옮기므로 확인됨·루브릭·주장 답을 그대로 가져가고, 그 머리(프로젝트)도 확인됨으로 둔다. 학력·자격처럼 AI가 칸을 나눠 채운 것은 미확인으로 두고 `맞음` 한 번으로 확인한다. 「제안」 그 밖의 옮긴 장면과 서술 칸에는 가져오기와 같은 주장 추출을 다시 돌려 주장 확인을 새로 받는다. 옛 주장 답(맞음·과장임 등)은 옮기지 않는다. 다만 이미 승인한 금지 표현과 "하지 않은 것"은 옮긴다
- 「제안」 바꾸는 시점은 모든 사용자에게 한 번에 온다(작성자의 판단). 그 전의 PR들은 새 표와 화면을 만들되 쓰지 않는 상태로 합치고, "바꾸기" PR 하나에서 옛 메뉴·가져오기·인터뷰를 닫고 자소서·이력서·채점이 새 표를 읽게 한다. 사용자마다 옮겼는지에 따라 기능이 갈리는 길은 만들지 않는다. 옛 표에 쓰는 길이 바꾸기와 함께 닫히므로, 옮긴 뒤 옛 표에만 들어가는 수정이 생기지 않는다
- 「제안」 옮기기는 바꾸기 배포 뒤 사용자마다 한 번, 앱의 어느 화면이든 처음 들어왔을 때 돈다. 메뉴를 열지 않는 사용자도 옮겨진다. AI를 부르므로 배포 때의 마이그레이션에서는 돌리지 않는다. 옮기는 동안 "기록을 새 구조로 옮기는 중"을 보이고, 실패한 항목은 "옮기지 못함"으로 남겨 다시 시도할 수 있게 한다. 옮긴 결과를 보여 주고 사용자가 고칠 수 있다
- 「제안」 옛 표는 옮긴 뒤에도 바로 지우지 않는다. 모든 사용자가 옮기고 사용자가 결과를 확인한 뒤, 따로 PR로 지운다(판단표 ② 반드시 묻기)
- 「제안」 옛 기록을 가리키던 것들
  - 제출본(5-3): 얼린 복사본이라 그대로 둔다(경험 이름까지 얼려 두었다)
  - 이력서 공통본·맞춤본과 자소서의 고른 경험·답: 옛 기록 id를 가리키므로 "기록 구조가 바뀌어 다시 만들어야 합니다"로 표시하고, 다시 만들기를 누르면 새 구조로 만든다. 제출로 잠긴 공고는 건드리지 않는다
  - 공고 점수(4-2): 지원할 때 얼린 점수는 그대로. 아직 지원하지 않은 공고의 요구 사항 분석은 다음 `다시 보기` 때 새 구조로 매긴다

### 5.11 쌓는 방법

- 가져오기(노션 zip, 글, 파일): 「제안」 AI가 자료를 새 구조로 나눈다(이력 사실은 해당 메뉴로, 경험은 머리와 장면으로). 가져온 것은 모두 미확인이고 주장 확인을 거친다
- 직접 입력: 「제안」 이력 사실은 짧은 폼으로 넣는다(인터뷰 없음). 장면은 폼 또는 인터뷰
- AI 인터뷰: 「제안」 장면을 쌓는 인터뷰로 바꾼다. 머리를 고르고(또는 새로 만들고) 그 아래 장면을 묻는다. 루브릭 미달 보완 인터뷰는 장면에만 있다

## 6. 데이터

모두 「제안」이다. 이름과 칸은 빌더가 정하고, 모듈 규칙(`docs/conventions.md`)을 따른다.

- `experiences` 모듈의 새 표: 학력, 교육 과정, 경력, 공백, 자격·어학·수상, 프로젝트, 활동, 장면. 메뉴와 표를 1:1로 두는 것이 이 설계의 목적이다(4장). 다만 칸이 거의 같은 것(예: 공백과 교육 과정)을 한 표로 합칠지는 빌더가 정한다
- 장면은 머리 하나를 가리킨다(경력·프로젝트·활동 중 하나). 프로젝트는 경력 하나를 가리킬 수 있다
- 트랙별 사용 범위, 주장(claims), 인터뷰는 새 표를 가리키게 바꾼다
- 묻기의 답: 새 표 하나(5.6)
- 회사 조사 결과: `postings` 모듈의 새 표 하나(5.7)
- 공고의 제출 서류·뽑은 문항: 공고 표에 칸을 더한다
- 경력기술서: 이력서 표처럼 공통본·맞춤본을 담는 새 표, 또는 이력서 표에 서류 종류 칸을 더하는 방식 중 빌더가 정한다
- 자소서 문항: 유형 칸과 자유양식 항목 칸을 더한다
- `runAi()`: 서버 도구(웹 검색)를 쓸 수 있게 넓히고, 사용량에 검색 횟수 요금을 더한다. `AiPurpose`에 회사 조사·묻기·옮기기를 더한다

## 7. 개인정보

- 연락처 규칙은 그대로다
- 회사 조사에는 지원자 정보를 보내지 않는다(5.7)
- 묻기의 답은 경험 기록과 같은 수준으로 보관한다(다른 사용자에게 보이지 않음, 사용자 삭제 시 함께 삭제)

## 8. 판단표와 규칙

- 새 표, `package.json`(웹 검색에 SDK 갱신이 필요할 때), `src/modules/ai/**`, `CLAUDE.md`를 바꾸므로 각 PR은 판단표 ②에서 사용자에게 묻게 된다
- 옛 표 지우기는 따로 PR로 하고 사용자에게 묻는다

## 9. 만드는 순서 (「제안」)

계획 하나마다 새 세션에서 한다(판단표 ⑥). 계획마다 단계별로 합쳐 그동안에도 자소서·이력서·채점이 돈다.

1. **5-4 경험 기록 개편**: 새 표, 메뉴 화면, 확인 방식, 옮기기, 가져오기·인터뷰를 새 구조로, 자소서 고르기·이력서·채점·제출본이 새 표를 쓰게 바꾸기. 큰 계획이므로 안에서 "새 표와 옮기기 → 화면 → 기존 기능 잇기"로 나눠 합치되, 앞 단계는 쓰지 않는 상태로 합치고 마지막 "바꾸기" PR에서 한 번에 켠다(5.10)
2. **5-5 공고 서류와 자유양식**: 제출 서류·문항 읽기, 자유양식, 문항 유형, 필요할 때 묻기
3. **5-6 회사 조사**: 웹 검색, 조사 화면, 쓰기·숫자 검사에 잇기
4. **5-7 경력기술서**: 공통본·맞춤본, 검사, 제출본에 얼리기
5. 옛 표 지우기(사용자 확인 뒤)

그다음은 지금처럼 6(내려받기), 7(지원 현황, AI 사용량, 전체 삭제)이다.

## 10. 빌더에게 맡기는 것

- 표 이름과 칸의 세부, 공백·교육 과정처럼 비슷한 표를 합칠지
- 화면 배치와 문구(메뉴는 5.1의 구성을 따른다)
- 옮기기를 한 번에 돌릴지 항목별로 나눠 돌릴지, 실패 다시 시도 방식
- 회사 이름 정리 규칙과 조사 결과를 다시 쓰는 기준의 세부
- 묻기의 질문 수와 선택지 수(2~3개, 3~5개 안에서)
- 프롬프트 문구. 프롬프트 점검(`prompt-check`)을 새 AI 작업마다 둔다
- 이력 사실을 쓰기 단계에 사실 확인용으로 보낼지(5.5)
- 경력기술서를 새 표로 둘지 이력서 표를 넓힐지
