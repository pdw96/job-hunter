# AI가 더 맡는 개발 방식 설계

2026-11-17. 사용자와 브레인스토밍한 결과.

## 왜 하는가

개발에서 사람이 손대는 구간을 줄인다. 사람만 할 수 있는 일만 사람에게 남긴다. 사용자는 타자를 많이 치는 것을 싫어하고, 지금은 AI가 혼자 할 수 있는 일에도 사람의 답을 기다리며 멈춘다.

**사용자가 정한 원칙**: 새로 덧붙이기보다 덜어낸다. 직접 만든 장치(훅, 스킬, 스크립트)보다 공식 도구를 쓴다. 직접 만든 것은 낡으면 관리할 일이 생기기 때문이다.

## 목표

- 절차 때문에 멈추는 구간을 없앤다. 대신 AI가 채점해서 정한다
- 실제 서비스의 상태를 AI가 직접 본다. 사람이 결과를 옮겨 오는 일을 줄인다
- 판단할 때마다 채점 결과를 남기고, 계획이 하나 끝날 때마다 채점표를 점검한다

## 하지 않는 것

- 정해진 때 스스로 도는 작업(예약 실행, 오류가 나면 저절로 PR을 여는 것). B로 써 본 뒤에 다시 정한다
- 제품 코드의 변경. 이 작업은 일하는 방식과 문서만 바꾼다
- 새 커스텀 훅, 스킬, 스크립트

## 실패로 보는 것 (돌아가더라도)

- AI가 사용자 승인 없이 자기 권한을 넓힌다
- 절차 문서(`CLAUDE.md`, `/ship`, 새 판단표 문서)가 지금보다 길어져, 읽고 관리할 것이 늘어난다
- 자동으로 합친 변경이 실제 데이터를 망가뜨린다
- 점수는 남기는데 아무도 다시 보지 않아 의식(儀式)이 된다

## 제약

- `main`에 합치면 실제 서비스에 배포된다. 실제 서비스 빌드는 마이그레이션을 적용하므로 되돌리기 어렵다
- 비밀 값은 사용자만 넣는다. 연락처는 AI에 보내지 않는다
- 실제 서비스 로그에는 세션 토큰과 사용자 id가 들어 있다. PR, 문서, 커밋에 옮겨 적지 않는다
- Codex 검토가 시작되는 때: PR을 열 때, 초안을 풀 때, `@codex review` 댓글을 달 때
- 작업 환경에서는 채용 사이트와 사용자 키로 쓰는 Claude API에 닿지 않는다
- AI가 합치려면 사용자가 미리 허락한 규칙이 있어야 한다. 사용자가 승인한 판단표가 그 허락이다

## 방법 (고려한 것과 고른 것)

| | A. 규칙만 덜기 | **B. A + 공식 도구 연결 (골랐다)** | C. B + 스스로 도는 작업 |
|---|---|---|---|
| 내용 | 문서를 고쳐 멈추는 지점을 줄인다 | 위에 더해, Vercel 연결로 배포·오류를 AI가 직접 보고, 위험이 낮은 PR은 AI가 합친다 | 위에 더해, 배포할 때마다 점검을 돌리고 오류가 나면 고치는 PR을 연다 |
| 좋은 점 | 가장 작다 | 이미 연결된 도구만 쓴다. 원칙에 맞는다 | 손이 가장 덜 간다 |
| 아쉬운 점 | 가장 번거로운 "결과 전달"이 남는다 | 실제 자료로 써 보는 일은 남는다 | 예약 장치와 점검 경로를 새로 만든다. AI 사용료가 계속 나간다 |

**사용자가 B를 골랐다.** 그리고 정해진 숫자(예: "재검토 최대 3번") 대신 **기준으로 채점해서 정하자**고 했다. PR #7은 5회차에서도 진짜 결함이 나왔으니, 정해진 숫자였으면 놓쳤을 것이다.

## 설계

### 1. 판단표 문서: `docs/decision-rubrics.md`

판단 지점마다 같은 형식을 쓴다.

- **반드시 묻기**: 점수와 상관없이 사람에게 묻는 조건. 채점하지 않는다
- **기준**: 기준마다 높음/중간/낮음이 무엇인지 정하고, 왜 그 기준인지 한 줄을 붙인다
- **결정 규칙**: 점수 구간마다 할 일. 애매한 구간은 사람에게 묻는다
- **마지막 점검**: 날짜와 그때 바뀐 것

판단 지점과 기준 초안은 아래와 같다. 정확한 점수와 구간은 만드는 사람이 정한다.

**① Codex 재검토**: 지적을 고친 뒤 다시 받을지

| 기준 | 높음 (다시 받기 쪽) | 낮음 (멈추기 쪽) |
|---|---|---|
| 지난 지적의 심각도 | 보안, 데이터 손실, 서버 멈춤 | 문구, 사소한 경우 |
| 고치면서 새로 쓴 코드 양 | 많음 | 몇 줄 |
| 줄어드는 추세 | 지적 수가 그대로이거나 영역이 넓어짐 | 줄고, 같은 곳만 다듬음 |
| 영역의 위험도 | 외부 입력, 주소 열기, 로그인, AI에 보내는 자료 | 화면, 문서 |
| 테스트로 덮였는지 | 고친 경우에 테스트 없음 | 모두 테스트 있음 |

반드시 묻기: 같은 지적이 되풀이된다. 고치려면 설계를 바꿔야 한다. Codex의 지적이 틀렸다고 보여 반박하려 한다.

**② 합치기**: AI가 합칠지, 사용자에게 물을지

반드시 묻기: 마이그레이션이 있다, 데이터를 지운다, 로그인·접근 허용·연락처 처리를 바꾼다, 돈이 드는 새 외부 서비스를 쓴다, 비밀 값이 필요하다, CI나 Codex가 끝나지 않았거나 지적이 남았다.

기준: 바뀐 영역의 위험도, 테스트로 덮인 정도, 합친 뒤 AI가 혼자 확인할 수 있는지(Vercel 로그로 볼 수 있는가, 실제 계정이 있어야 하는가), 변경의 크기, 사용자가 직접 보는 동작이 바뀌는지.

**③ 계획 승인**: 계획 문서를 사용자에게 승인받을지

설계 문서에 이미 정해진 것만 따르는 계획은 승인을 기다리지 않고 구현에 들어간다. 사용자는 PR에서 계획을 본다. 설계에 없던 결정이 있으면 그 결정만 번호 선택지로 묻는다. 계획 문서 전체를 읽게 하지 않는다.

기준: 설계에 없던 결정인지, 되돌리기 쉬운지, 비용이 드는지, 사용자가 보는 동작이 바뀌는지.

**④ 배포 후 확인**: 합친 뒤 누가 확인할지

AI가 Vercel에서 배포가 끝났는지, 빌드 기록에서 마이그레이션이 적용됐는지, 배포 뒤 새 실행 오류가 있는지 본다. 사용자에게는 실제 계정, 실제 채용 사이트, 실제 AI의 답의 질이 있어야 확인되는 것만 부탁한다. 무엇을 눌러 보면 되는지 한두 줄로 적는다.

**⑤ 실제 사이트 구조 확인**: 채용 사이트에 맞춘 수정이 필요할 때

먼저 Nimble로 공개 공고 주소 하나를 읽어 본다. 안 되면 지금처럼 사용자에게 저장한 페이지를 받는다. 로그인이 필요한 페이지는 Nimble로 열지 않는다.

**⑥ 새 세션**: 언제 새로 열지

한 세션으로 이어 간다. 구현은 작업마다 새 하위 에이전트에 맡긴다(`superpowers:subagent-driven-development`). 다음 낌새가 보이면 사용자에게 새 세션을 권한다: 이미 정한 것을 다시 묻는다, 같은 실수가 되풀이된다, 문서와 다른 내용을 사실처럼 말한다.

### 2. 기록: PR 본문의 "판단 기록"

따로 기록 파일을 만들지 않는다. PR 본문 끝에 "판단 기록"을 두고, 판단할 때마다 한 줄을 더한다.

```
- Codex 재검토 2회차: 심각도 높음, 새 코드 중간, 추세 그대로, 영역 높음, 테스트 있음 → 다시 받기
- 합치기: 반드시 묻기 없음, 점수 낮음 → AI가 합침
```

판단표를 바꾼 뒤의 기록에는 판단표의 마지막 점검 날짜를 함께 적는다. 어느 판단표로 채점했는지 알 수 있게 한다.

### 3. 점검: 계획이 하나 끝날 때마다

`CLAUDE.md`의 "지금 상태"를 고칠 때 같이 한다. 예약 장치를 쓰지 않는다.

- **볼 것**: 지난 점검 뒤 PR들의 판단 기록, 사용자가 바로잡은 일, AI가 합친 뒤 Vercel에 생긴 오류, "멈추기"로 정한 뒤에 나온 결함(놓친 것)
- **적는 곳**: 그 계획 문서 끝의 "판단표 점검"에 판단표마다 맞은 것과 틀린 것을 적는다
- **고치는 권한**: 더 조심하는 쪽(묻는 조건을 더하거나, 다시 받기 쪽으로 기울이기)은 AI가 바로 고친다. 덜 묻는 쪽(AI 권한을 넓히기)은 사용자에게 번호 선택지로 묻는다. 판단표를 자동으로 느슨하게 고치지 않는다. 앱 설계의 "배점을 자동으로 고치지 않는다"와 같은 생각이다

### 4. 덜어내기

- `CLAUDE.md`
  - "새 세션은 ... 다음 작업 진행해" 부분을 한 세션 원칙으로 바꾼다. 다른 세션이 이어받을 때를 위해 "지금 상태"는 그대로 둔다
  - "순서"와 "합치기 전" 규칙은 판단표를 가리키게 줄인다
- `/ship`: 5~7번(Codex 기다리기, 지적 처리, 합칠지 묻기)을 판단표 ①②를 따르게 바꾸고, 8번은 ④를 따르게 한다. `/ship`을 남길지, 공식 도구로 대신할지는 만드는 사람이 정한다. 단, 절차 문서 전체의 길이가 지금(`CLAUDE.md` 56줄 + `/ship` 22줄)보다 길어지지 않아야 한다
- PR #15(단계마다 쓸 스킬을 더 적는 것)는 이 방향과 반대이므로 닫는다
- 고친 파일의 테스트를 돌리는 훅은 둔다. 잘 쓰이고 있고 불만이 없었다

### 5. 쓰는 공식 도구

| 도구 | 쓰는 곳 | 확인한 것 |
|---|---|---|
| Vercel MCP | ④ 배포 상태, 빌드 기록, 실행 오류 | 프로젝트 `job-hunter`를 찾았고 실행 오류를 읽었다. 첫 확인에서 아무도 몰랐던 DB 연결 끊김 오류를 찾았다(별도 작업으로 넘김) |
| GitHub(MCP) | ② 합치기, ① `@codex review` 댓글, 스레드 해결 | 지금도 쓰고 있다. 자동 합치기(auto-merge)는 저장소 설정과 필수 검사가 있어야 한다. 없으면 검사가 통과한 뒤 바로 합친다 |
| Nimble | ⑤ 공개 공고 페이지 읽기 | 사람인용 추출 틀은 없다. 그냥 읽기가 되는지는 계획 단계에서 공고 하나로 시험한다 |
| superpowers 하위 에이전트 방식 | ⑥ 구현을 새 컨텍스트에서 | 이미 설치돼 있다 |

## 누가 정했는가

**사용자가 정한 것**: B 방식. 정해진 숫자 대신 기준으로 채점하기. 점수와 근거를 남기기. 판단표가 낡으므로 계획마다 점검하기. 덜어내고 공식 도구를 쓴다는 원칙. 계획마다 새 세션을 여는 규칙을 없애는 데 반대하지 않았다.

**설계하며 정한 것(사용자가 확인할 것)**: 반드시 묻기 목록. 고치는 권한을 나누는 방식. PR 본문에 기록하기. ⑤의 Nimble 사용. PR #15를 닫기. 절차 문서가 길어지지 않는다는 상한.

- 기준별 점수(예: 0/1/2)와 결정 구간의 정확한 값
- PR 본문 "판단 기록"의 정확한 형식
- `/ship`을 고칠지, 공식 도구로 대신할지
- 판단표 문서 안의 정확한 문장
