# 냉정한 검토와 원래 방향 (2026-11-26)

사용자와 한 세션 동안 프로젝트를 비판적으로 돌아봤다. 이 문서는 그 결론이다. 새 계획을 세우기 전에 먼저 읽는다.

- "합의한 것"은 사용자가 말했거나 확인한 것이다. 그대로 따른다
- "제안"은 검토자의 추천이고 아직 정하지 않았다. 계획에 넣기 전에 사용자에게 묻는다
- 시안: [Job Hunter 시안](https://claude.ai/artifact/WBJJzhimb6DBzN8px4aZmf)(비공개). 같은 파일이 `docs/reviews/2026-11-26-direction-mockup.html`에 있다. 지어낸 예시 데이터만 들어 있다

| 지원 공고 / 제출본 | 2 / **0** |

## 2. 검토에서 나온 것

### 2.1 거꾸로 만들었다

사용자가 가장 중요하다고 본 것은 경험 정리(기준점)다. 그런데 그 단계는 끝나지 않았고, 서류 기능(5-1~5-7)만 두꺼워졌다. 서류 기능은 기준점이 차야 평가할 수 있으므로, 지금은 검증할 길이 없는 채로 쌓여 있다. 실제 공고로 하는 확인은 "공고 자동 가져오기를 만들 때 함께" 하기로 미뤄져 있다. 확인을 다음 기능의 조건으로 걸면 계속 밀린다.

### 2.2 구조를 비싼 곳에서 실험했다

구조가 마음에 들지 않아 계속 바꿨다(사용자). 바꿀 때마다 마이그레이션, 옮기기, AI 옮기기, 다시 옮기기, 잘못 이은 연결 고치기, 서류 기능 7개 수정이 따라왔다. 그동안 기준점은 흔들려 채울 수 없었다. 확인된 사례가 2/17에 멈춘 큰 원인이다.

- "좋은 구조"의 기준이 적혀 있지 않았다. 그래서 바꾸기를 끝낼 수 없었다
- 저장 구조의 문제와 보이는 방식의 문제가 섞였다

### 2.3 저장 구조: 묶음이 DB 설계에 박혀 있다

나무 모양(기관 → 프로젝트 → 사례)이 나무로 저장되어 있지 않다. 부모가 될 수 있는 종류마다 칸을 둔다.

```
experiences_projects:      job_id, education_id, course_id, activity_id  (넷 중 하나 이하)
experiences_scenes:        job_id, project_id, activity_id, education_id, course_id  (다섯 중 하나)
experiences_record_claims: scene_id, job_id, project_id  (셋 중 하나)
```

그래서 새 묶음을 허용할 때마다 칸을 더하는 마이그레이션이 필요하다(이력 묶어 보기에서 칸 3개). 화면과 서류 기능은 흩어진 칸에서 나무를 다시 짜 맞춘다. 깊이도 3단으로 고정이다. 담당 업무는 `experiences_jobs.duties`(글 목록)라서 사례를 업무에 붙일 수 없다.

옮기기 결과에서 사례 17개 중 8개가 바로 위 프로젝트·활동과 이름이 같다. 옮기기가 프로젝트마다 똑같은 사례를 하나씩 만든 것이고, 프로젝트와 사례의 구분이 실제 경험과 맞지 않는다는 신호다.

### 2.4 품질 점검은 안전만 잰다

관리 화면 프롬프트 점검(115줄)은 금지 표현, 기록에 없는 숫자, 글자 수, 엉뚱한 경험 고르기만 본다. 글이 좋은지는 재지 않고, 예시도 지어낸 기록 하나다. 문단에는 `edited: boolean`만 남고 AI가 처음 쓴 글은 덮인다. 사용자가 무엇을 고쳤는지가 가장 좋은 평가 자료인데 버려진다. 지시문(`WRITE_SYSTEM`)은 대부분 금지이고, 좋은 글을 쓰는 방법은 거의 없다.

다만 기준점이 차기 전에는 우선순위가 낮다.

## 3. 원래 그린 방향 (사용자, 2026-11-26)

```
기준점(DB)
 ├ 기준 이력서 (사람인식 섹션·칸)
 └ 경험 사례 (이력 항목에 붙는 장면)
        ↓
기준점을 바탕으로 한 스킬·방향 추천 (AI)
        ↓
공고 서치 (여러 구직 사이트) → 같은 회사 공고는 하나로 합치고 플랫폼 이름을 여러 개 붙임 (AI)
        ↓
맞는 공고의 회사별 이력서·경력기술서·자소서 작성 (AI)
```

사용자는 "부족한 점이 있는데 표현을 못하겠다"고 했다. 검토자가 짚은 빈 곳:

1. **내가 원하는 조건**이 없다. 기준점은 내가 가진 것뿐이다. 지역, 연봉, 규모, 고용 형태, 제외 조건이 있어야 갈 곳을 찾는다
2. **내가 결정하는 관문**이 없다. 공고마다 지원·보류·제외는 사람이 고르고, AI가 쓴 서류는 사람이 검토한다
3. **결과가 돌아오는 고리**가 없다. 제출 뒤 서류 합격·탈락이 쌓여야 어떤 경험과 방향이 통했는지 보고 기준점과 추천을 고친다
4. 작게: 기준점을 채우는 방법, 회사별 재료(회사 조사), 매일 도는 주기, 추천의 결과물이 검색 조건이어야 한다는 점

채운 흐름과 지금 앱:

| 단계 | 누가 | 지금 앱 |
|---|---|---|
| 0. 기준점 채우기 (직접 입력·가져오기·인터뷰) | 나, AI | 일부 |
| 기준점: 기준 이력서 · 경험 사례 · (제안) 자기소개 재료 · (제안) 내가 원하는 조건 | | 일부 |
| 1. 방향·스킬 추천 → 검색 조건 | AI | 없음 |
| 2. 공고 모으기 (매일, 여러 사이트, 중복 합치기) | AI | 없음 |
| 3. 공고 고르기: AI 점수 → 내가 지원/보류/제외 | 나 | 있음 |
| 4. 회사 조사 ([지원]일 때만) | AI | 있음 |
| 5. 서류 작성 → 내가 검토·수정 | AI, 나 | 있음 |
| 6. 제출 + 지원 현황(마감·결과) | 나 | 일부(제출본만) |
| 7. 결과로 되돌아보기 → 기준점·추천 고치기 | AI, 나 | 없음 |

가운데(3·4·5)는 두껍고 앞(0·1·2)과 끝(6·7)이 비어 있다.

## 4. 합의한 것

- **기준점은 DB 하나다.** 회사별 서류는 기준점에서 골라 다시 쓴다
- **기준 이력서는 사람인 이력서처럼 관리한다.** 정해진 섹션과 칸을 한 페이지에서 위아래로 본다
- **회사 조사는 [지원]을 누른 공고만 한다**(지금도 그렇다). 공고를 고를 때는 공고 원문과 가벼운 회사 정보로 충분하다
- **지원동기·포부는 큰 단계가 아니다.** 서류를 쓸 때 문항이 요구하는데 기준점에 재료가 없으면, 그때 연결 후보를 보여 주고 고르게 한다
- **자소서 문항이 있는 공고와 자유양식을 구분한다**(지금도 그렇다). 자유양식은 AI가 공고와 기준점을 보고 항목·순서·글자 수를 이유와 함께 추천하고, 사람이 체크를 바꾸거나 직접 추가한다(사용자가 원함). 지금은 기본 체크(지원동기·직무 역량·포부)가 모든 공고에서 같다
- **평소 업무는 "사례"로 따로 띄우지 않는다.** 경력 아래는 담당 업무 → 성과 한 줄 → 접힌 이야기(상황·행동·결과)다. 이야기는 자소서를 쓸 때 꺼낸다
- **모든 섹션에 같은 규칙을 쓴다.** 한 일(담당 업무·프로젝트·교육 과정·대외활동·개인 프로젝트)은 사실 칸 → 성과·한 일 한 줄 → 접힌 이야기다. 증명만 하면 되는 것(학력·자격·어학·수상·공백)은 한 줄이고, 수상은 관련 프로젝트를 가리킨다. 학교·교육 과정 안의 프로젝트는 그 아래에 붙는다

## 5. 제안 (아직 정하지 않음)

1. **트랙별 공통본을 없애고, 트랙은 기준점에 거는 필터(사용·요약만·제외)로만 둔다.** 기준점이 두 개가 되어 어긋나는 것을 막는다. 사용자는 "잘 모르겠다"고 했다. 지금 트랙은 1개다
2. **기준점에 "자기소개 재료"를 둔다.** 회사와 상관없는 커리어 전환 이유, 가치관, 성격, 목표다. 지금은 공고를 거쳐야만 생기고 회사별 쪽 표(`applications_answers`)에 흩어져 쌓인다. 사용자의 원래 그림에는 없었다
3. **기준점에 "내가 원하는 조건"을 둔다.** 2·3단계에 필요하다
4. **직접 적거나 고친 것은 저장하는 순간 확인된 것으로 본다.** 확인 단계는 노션 등에서 가져온 것에만 둔다. 확인된 사례가 2/17에 멈춘 부담을 줄인다
5. **저장 구조: 모든 기록이 공통 바탕(`id`, 종류, `parent_id`, 순서)을 갖고, 종류별 칸만 따로 둔다.** 무엇을 어디 아래에 둘지가 데이터가 되어 칸을 더할 일이 없어진다. 담당 업무도 기록이 되어 성과·이야기를 붙일 수 있다. 크게 바꾸기 전에 시안(②)과 사용자의 실제 경험으로 모양을 먼저 맞춘다
6. **순서: 서류 기능(5단계)을 더 키우지 않는다.** 기준점(0) → 공고 모으기 가능성 조사(2: 사이트별 공식 API와 약관, 하루 안에) → 방향 추천(1) → 지원 현황과 결과 고리(6·7)
7. **옛 표 지우기는 새 기준점 구조를 정한 뒤로 미룬다.** 구조가 또 바뀌면 지우는 일과 옮기는 일이 겹친다
8. **품질은 나중에:** AI가 처음 쓴 글을 고친 글과 함께 저장하고, 실제 기록으로 앱과 Claude 대화창을 비교한다. 지시문에 좋은 글을 쓰는 방법과 예시를 넣는다
9. **성공 지표를 하나 둔다.** 예: 이 앱으로 만든 서류를 낸 지원 수

## 6. 남은 검토 주제

아직 하지 않았다. 한 번에 하나씩 한다.

- C 보안·개인정보(공고 주소 읽기의 내부 주소 차단, 공고 속 숨은 지시, 연락처가 AI로 새는 길, 사용자 간 데이터 분리)
- D 운영·비용·장애 대응(AI 비용 상한, 장애 알아채기, 마이그레이션 되돌리기, 백업)
- E 테스트의 신뢰도(로컬 가짜와 실제 서비스의 차이)
- F 프로세스 무게(사용자 몇 명짜리 프로젝트에 판단표·계획 문서·스킬이 많지 않은가)
- 1 바이브코딩(AI가 짠 코드의 품질)
- 2 AI 엔지니어링 최신 흐름과의 차이
